## 0. 最重要的发现（请先读这三条）

### 0.1 【推翻设计前提】简报 C1.1/C1.3 的「单线程执行器」机制在真实请求路径上不成立

简报 C1 的核心论断是：**全部同步视图经 `sync_to_async(thread_sensitive=True)` 走同一个进程级单线程执行器，于是「8 个并发请求 = 1 个线程 = 1.61s 串行」**。实测**不成立**。

| 场景 | 命令 | 实测结果 |
| --- | --- | --- |
| A 简报 C1.3 原样复现（直接调 asgiref，无上下文） | `_probe_c1_mechanism.py` STEP1 | `thread_ids=[100976] wall=1.61s` ✅ 简报测量本身没错 |
| B Django ASGI 真实请求路径（daphne，`backend.asgi:application`） | `probe_concurrency.py` 场景 C | N=8 → **0.25s**、N=20 → **0.27s**；慢中间件记录 **最大同时 sleep=21、50 个不同线程** |
| C 同一 `ThreadSensitiveContext` 内多段同步工作（= 单请求内） | `_probe_c1_mechanism.py` STEP1/3 | 仍单线程（这是设计意图：保证单请求内的线程亲和性） |

**根因（逐行核对框架源码）**：
- `backend/.venv/Lib/site-packages/django/core/handlers/asgi.py:169` → `async with ThreadSensitiveContext():`，**每个请求**都会新开一个上下文；
- `backend/.venv/Lib/site-packages/asgiref/sync.py:467-478` → 有该上下文时使用**该上下文专属**的 `ThreadPoolExecutor(max_workers=1)`；
- `backend/.venv/Lib/site-packages/asgiref/sync.py:488` → 简报引用的 `single_thread_executor` 只在**没有**该上下文时才命中。

**直接推论**：简报 C1.5 的两条验收（「并发 20 个请求总墙钟接近单请求」「并发期间另一个请求延迟 < 1s」）
**在改造前的 daphne 单进程形态下就已经达标**（N=20 墙钟 0.27s、在途追加请求 0.22s）。
C1-a（WSGI+gunicorn 进程分离）对**并发度**的收益在本机不可观测（WSGI 多线程 N=20 = 0.23s，与 ASGI 0.27s 同量级）。

> Lead 已用独立最小探针复核并采纳（三档对照：无上下文 1.61s/1 线程、每任务上下文 0.20s/8 线程、同上下文内 8 任务 1.61s/1 线程），
> 已在报告、`docs/运维约束整改设计说明.md` §0.1 落地更正。

**这不等于「C1-a 必须撤掉」**：它仍有独立价值——① 线程数**有界**（gunicorn 4×8=32，而 ASGI 路径是每请求一线程、无上限，100 并发即 100 线程）；
② 长连接（Socket.IO）与短请求（REST）进程隔离，可独立重启/限流/观测；③ 满足「HTTP 走同步 WSGI 栈」的运维习惯。
但它同时**新增**了跨进程总线、`/_internal/` 门禁白名单、第二个 systemd unit、nginx 双上游等**新风险面**，
是否启用属运维取舍（且 `.env` 层面有回退路径）。详见 §4 风险排序。

### 0.2 【重要限定】`SQLITE_TUNING_ENABLED=false` **不能**把已经 WAL 化的库变回 `delete`

`journal_mode` 是 **SQLite 库文件的持久属性**，一旦库文件被改成 WAL，之后任何连接（哪怕完全不发 PRAGMA）看到的仍是 `wal`。

| 副本状态 | `SQLITE_TUNING_ENABLED=false` 后的实测 PRAGMA |
| --- | --- |
| **全新库**（本次整改尚未 WAL 化） | `journal_mode=delete`、`busy_timeout=5000`、`synchronous=2`、`OPTIONS={}` ✅ 完全等于改造前 |
| **已被 WAL 化**的库（= 现在 `backend/db.sqlite3` 的状态） | `journal_mode=wal`（**保持**）、`busy_timeout=5000`、`synchronous=2`、`OPTIONS={}` ⚠️ |

**结论**：设计说明 §3「关掉开关 = 现场秒回退到改造前」对 `busy_timeout`/`synchronous`/`OPTIONS` 成立，对 `journal_mode` **需要额外一步**：
停服后对库执行 `PRAGMA journal_mode=DELETE`（或换回改造前的库文件）。Lead 已采纳并写入设计说明 §0.2、`.env.example`、报告 §5。

### 0.3 【重要限定】三个开关不足以逐字节回退，需要第 4 个开关

实测：只设 `SQLITE_TUNING_ENABLED=false` + `AUDIT_HTTP_ERROR_MODE=all` + `REALTIME_BUS=local` 时，
`/api/auth/me` **仍返回 `ETag` 响应头**（`static_checks.py` 的 `J2-three-switches-still-emit-etag`）。
再加上 `AUTH_ME_CONDITIONAL_ENABLED=false` 才完全不返回 ETag（`J2-fourth-switch-restores`）。
另需注意：零配置本身**并不等于**改造前（C2 与审计采样默认生效，见 §5 表）。

## 8. 验收方独立判断：是否可用于赛前上线

真正的风险不在代码正确性，而在三处**口径与取舍**：

1. **必须先更正 C1 的立项依据再决策**（R1/R2）。C1.5 的并发验收在改造前就已达标；C1-a 现在的价值是「有界并发 + 进程隔离」。
   若赛前时间紧，**可以选择只上线 C2+C3 与「只启用 gipfel.service（hub≡local）」**，把 C1-a 的双进程拆分留到赛后——
   这条路径的回归面最小（新增的 `deploy/gipfel-wsgi.service`、nginx 双上游、`REALTIME_BUS=forward` 都不生效）。
2. **回退手册必须补两步**（R3/R4）：已 WAL 化的库需显式 `PRAGMA journal_mode=DELETE`；逐字节回退需第 4 个开关
   `AUTH_ME_CONDITIONAL_ENABLED=false`。否则「一键回退」在现场会得到与预期不符的行为。
3. **必须补齐真机验证**（§3）：至少 `nginx -t` + gunicorn 多进程实跑 + 双进程实时广播端到端 + 100 客户端压测。
   本机把「结构正确」验到了，但「在 Linux 上真的跑起来」没有验过——这是本次验收**最大的未覆盖率**。

上线前建议的最小动作清单（按优先级）：
1. 目标机跑 `systemd-analyze verify` + `nginx -t` + `systemctl start` 三件套，看 `journalctl` 有无 EAFNOSUPPORT/权限错误；
2. 真机做一次「2 标签 + 1 写操作」的实时广播验证（forward/redis 两条路径各一次）；
3. 真机做一次「快照 → 破坏 → 回退」并确认 `-wal/-shm` 清理步骤（本机已在副本上验通，真机只差路径/权限）；
4. 按 §5 决定审计取证口径（R6），必要时把采样率调回 1.0；
