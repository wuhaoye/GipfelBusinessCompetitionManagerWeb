## 0. 结论摘要

### 0.1 一句话结论

**系统是一个「通用主数据 + 可编程合同引擎 + 股票引擎」的赛事平台，而不是规则书的实现。**

规则书真正被实现的只有两处：**股票撮合/K 线/持仓**（Update 1.0 第三部分）与**物流里程—运费—碳排计价**（通过合同效果）。公司全生命周期的资金、权益、评分类规则几乎整体缺失 —— 这些规则占了 Update 1.0 前 9 页与 Update 3.0 的 P6–P23。

这不是"代码有 bug"，而是**规则与系统之间缺少一层模型**。

### 0.2 三个"会让比赛办不下去"的问题

| # | 问题 | 后果 |
| --- | --- | --- |
| **1** | 系统**没有复式记账与财务报表**，而 Update 3.0 规定"所有会计科目核算严格遵循借贷记账法"、评分全部取财报口径 | 赛后**没有任何客观依据**评出奖项；赛程规定的"各代表与审计核对当日账表"**无法执行** |
| **2** | **选手账号在本系统里几乎没有写权限**；且每个账号**同一时刻只允许一台设备在线** | 比赛退化为"一名超管在主席台逐家录数据"；主席团账号无法多人共用 |
| **3** | **赛事实际的 4 份数据文件一行都进不了系统**（3 份静默导入为空比赛、退出码 0；1 份报错退出） | 零件/产品配比、地点价、基建指标、全域里程表只存在于 Excel，系统内验算与计价失去基准 |

### 0.3 缺陷总览

| 级别 | 条数 | 含义 |
| --- | --- | --- |
| **P0** | 6 | 不修则比赛无法按规则完成，或赛后无法判定名次 |
| **P1** | 8 | 会造成现场混乱、需要人工绕过，或使规则形同虚设 |
| **P2** | 8 | 摩擦与体验问题 |
| **合计** | **22** | 另附规则书自身缺陷 20 条（§5） |

## 1. 根因分析：为什么规则大面积落不了地

### 1.1 没有"公司持有资产"这一层模型

规则书通篇在讲"公司购置仓库/生产线/矿点/载具"（Update 1.0 P13–P23），并要求**按财年直线法计提折旧**（P13.4）、**以固定资产抵押贷款**（P8）。

但系统里这些实体是**比赛级主数据，没有任何指向公司的外键**：

```python
# backend/apps/warehouses/models.py:17-26
name = models.CharField(max_length=255)
capacity = ExactDecimalField(max_digits=60, decimal_places=4)
price = ExactDecimalField(max_digits=60, decimal_places=4)
type = models.CharField(max_length=16, choices=TYPE_CHOICES)
competition = models.ForeignKey("competitions.Competition", ...)   # ← 只挂在比赛上
```

`warehouses` / `production_lines` / `vehicles` / `materials` / `parts` / `products` 全部如此。
**没有"谁拥有什么、拥有多少、值多少、折旧到几成"的任何载体**，因此"购置 / 持有 / 抵押 / 折旧"这四类规则**没有落地位置**，只能靠改写公司产业卡片上的数字字段近似表达。

### 1.2 没有"区域经济指标"实体

```python
# backend/apps/regions/models.py:8-18
name = models.CharField(max_length=128)
description = models.TextField(null=True, blank=True)
competition = models.ForeignKey("competitions.Competition", ...)
overview_cards = models.TextField(default="[]")   # ← 只有卡片配置 JSON
```

`Region` **没有幸福度、人口、就业率、碳排放、人口承载力任何一个字段**。
基建的 9 项加成字段倒是齐全（`backend/apps/infrastructures/models.py:14-22`），但**没有任何消费方**——没有被加总到区域指标上，也没有参与任何财年结算。

**Update 3.0 给出的是三条完整的量化递推模型，系统一条都没有实现**（全文已完整恢复，见 [`V3_PARAMS.md`](audit/rules/V3_PARAMS.md)）：

**(1) 区域人口数量（logistic 模型，Update 3.0 P17）**

```
P(n+1) = min[ P(n) + ( P(n)·r·H/100 + ΔP_infra )·(1 − P(n)/k) , k ]
r = 3%/财年（基础人口增长率）；k = 人口承载力上限；ΔP_infra = 本期新建基建人口增加量
```

**(2) 区域幸福度（Update 3.0 P15）**

```
C = Q_s / Q_d                                   # 供需比
H = 0.6·C + 0.1·log10(P + 100) + 2·(T/P) + 0.2·(E/P)
P_sell = P_base · (1 + H/100) · (1 + (Q_d − Q_s)/Q_d(max))
变量：P=人口，T=高素质人才，E=碳排放量，Q_s=供应量，Q_d=需求量，
      P_base=商品基准价（= 商品成本 + 基础利润），P_sell=商品平均成交价
```

**(3) 劳动力薪资（Update 3.0 P5）**

```
w = w₀ · (1 + 0.9·[H/100]) · (1 + k₂·[T/P]) · ln(P + P₀)
w₀ = 1000（元/年/人），k₂ = 1.2，P₀ = 1000
```

**系统对照**：合同引擎的求值器**具备** `log10`/`ln` 等数学函数（`backend/apps/contracts/engine.py:737-739`），因此这三条公式**理论上可以用合同 DSL 手写出来**——但：
- 没有 `人口`、`高素质人才`、`承载力 k`、`基准价 P_base` 任何数据源（`Region` 无字段）；
- 全仓搜 `salary|薪资|wage|劳动力成本|labor_cost` — **零命中**，公式 (3) 完全没有落点；
- 唯一沾边的是股票引擎里一个简化碳因子（`engine.py:145-150`）与可配权重 `happinessImpact/carbonImpact`（默认 0.2/0.2，`engine.py:349-350`）——**与 Update 3.0 的 `0.6/0.1/2/0.2` 系数结构无关**。

即：规则书把区域经济写成了一个**可计算的动力学系统**，系统只提供了"能算的引擎"，**没有提供"被算的对象"**。

### 1.3 财年只是一个标签，不是状态机

```python
# backend/apps/competitions/models.py:26-42
class FiscalYear(models.Model):
    year = models.IntegerField()
    status = models.CharField(max_length=16, default="ACTIVE", choices=STATUS_CHOICES)
```

财年**没有阶段（阶段门禁）**。而规则书里大量规则是**跨财年门禁**：第 1 财年不开放贷款（Update 1.0 P8）、第 4 财年研发则第 5 财年才能生产（P22）、第 2 财年起才可贷款（P8）——**这些规则没有实现位置**。

## 2. P0 缺陷与方案（6 条）

### P0-1 无复式记账 / 无财务报表，而规则与评分全部依赖财报口径

**问题**（Update 3.0 P19「通用核算原则」逐字）：

> 所有会计科目核算严格遵循借贷记账法，核心规则为"有借必有贷，借贷必相等"，所有记账凭证（含采购、折旧、借款、结转等）均需满足该规则。
> 科目余额列报规则：资产类、成本类科目期末借方余额列报，负债类、所有者权益类科目期末贷方余额列报，损益类科目结转后无余额，不得列报。
> 固定资产折旧仅采用年限平均法（直线法）。
> 所有经济业务的核算均以银行存款为主要结算科目。

**系统现状**：全仓搜 `借贷` / `记账凭证` / `总账` / `科目余额` / `试算平衡` — **零命中**。
业务数据只有两种形态：合同引擎对产业字段做 ADD/SUB/SET，以及 `FundsAccount` 里的现金余额。**没有分录、没有科目、没有账簿、没有试算平衡、没有财务报表**。

**为什么是 P0**：

1. Update 3.0 P19–P23 的三套评分准则**全部取自财报科目**：毛利率 =（营业收入−营业成本）÷营业收入；净利率需剔除营业外收支；净资产增长率需"所有者权益 = 实收资本 + 资本公积 + 本年利润 − 利润分配"；资产负债率需"负债总额 ÷ 资产总额"；货币资金保障率需"银行存款 ÷ 短期借款"。**系统没有任何一项能算出来**——不是算错，是没有数据源。
2. Update 2.0 日程 7月29日 18:30 要求"**各代表与审计核对当日账表**"。系统无法产出任何公司的资产负债表/利润表/现金流量表，甚至没有**按公司导出**的功能（全仓导出只有 `preparation` 的准备清单归档与 Markdown 报告，`backend/apps/preparation/views.py:170`）。
3. 闭幕式要"颁发各产业奖项"（Update 2.0 P6），**没有评分就没有名次**。

**改进方案**

| 步骤 | 内容 |
| --- | --- |
| 1 | 新增 `ledger` app：三张表 `Account`（科目，含资产/负债/权益/成本/损益五类）、`JournalEntry`（凭证头：日期/摘要/财年/比赛/来源单据）、`JournalLine`（分录：科目/借/贷金额） |
| 2 | 强制不变式：**有借必有贷、借贷必相等** —— 在 `clean()` 与 `save()` 双重校验，并对同一凭证的分录做 `transaction.atomic()` 包裹；提供 `assert_balanced(entry)` 供单测与导入侧复用 |
| 3 | 合同效果 → 自动分录：在合同执行落账处按"合同类型 → 科目映射"生成分录；折旧按直线法每财年计提（需先有资产持有模型，见 P1-3/P2-5 的前置） |
| 4 | 报表：资产负债表 / 利润表 / 现金流量表，支持**按公司、按财年**查询与导出（CSV/Excel），供审计对账与赛后归档 |
| 5 | 科目余额列报规则按 Update 3.0 P19 实现（损益类结转为零、资产借方余额、负债/权益贷方余额） |

**验收标准**：任何不平衡凭证被拒；任意时点试算平衡；执行一份采购合同后银行存款与存货科目同步变动且试算平衡；三张报表可从分录重算得出，且导出文件与界面数字一致。

**工作量估计**：3 人日（内核）+ 2.5 人日（分录接入）+ 2 人日（报表）。

> **前置警告**：分录落地需要"这笔业务动的是哪个科目"的语义，而当前业务载体是"产业卡片上的数字字段"。因此 P0-1 与 §1.1 的资产持有模型（见 P1-3、P2-5）在实施顺序上互相纠缠，建议先做最小科目映射（银行存款/存货/实收资本/主营业务收入/成本），资产类科目随资产模型扩展。

### P0-2 选手账号几乎没有写权限 + 单账号单设备，比赛会退化成"主席台代录"

**问题 (a)：权限模型与赛制不匹配**

| 选手必须做的事 | 规则出处 | 需要的权限 | PLAYER 是否持有 |
| --- | --- | --- | --- |
| 下单/撤单买股票 | Update 1.0 P30–P31 | `stock:view` | ✅ 持有 |
| 签署购销/物流/借款等合同 | Update 1.0 P15–P23（通篇） | `contract:manage` + `contract:execute` | ❌ **仅 COMPETITION_ADMIN 持有** |
| 填写经营数据（产量/库存/价格） | Update 1.0 P13–P22 | `company:manage` | ❌ **需超管显式 `allowExtras=true` 才能授予** |
| 发布/调整市场需求 | Update 1.0 P21 | `data:region:edit` | ❌ 同上 |

证据：

```python
# backend/apps/common/permissions.py:357-365
"PLAYER": {
    "defaultPermissions": BASE_VIEW_PERMISSIONS,   # 17 个全部是 :view
    "grantCeiling": BASE_VIEW_PERMISSIONS,         # 上限也只有 :view
    "grantExtras": [],
},
```

```python
# backend/apps/common/permissions.py:298-316  BASE_VIEW_PERMISSIONS 全为 :view
# backend/apps/company_fields/views.py:25-26
_VIEW_PERM = "company:view"
_MANAGE_PERM = "company:manage"      # ← 写产业字段需要它
```

`contract:manage` / `contract:audit` / `contract:execute` 只在 `COMPETITION_ADMIN` 的默认集里（`permissions.py:342-347`）。

> **注**：早期审计报告的 I-13 记录"扩展集永远授不出去"。**该缺陷已修复**（`permissions.py:369-406` 现在支持 `allowExtras=true` 显式放开）。所以 `company:manage` **可以**授予 — 但必须由超管带 `allowExtras=true` 调 API，**账号管理界面没有这个开关**。

**问题 (b)：单账号单设备是硬约束**

```python
# backend/apps/auth/views.py:161-168
user.token_version = (user.token_version or 0) + 1
user.save(update_fields=["token_version", "updated_at"])
...
kick_user_sessions(user.id, reason="token_version_mismatch")
```

**每次登录都递增**，且**真正断开旧 socket 连接**。这是有意的安全设计（防账号盗用），但直接后果是：**一个 `COMPETITION_ADMIN` 账号不能同时被两名主席团成员使用**；若用 `SUPER_ADMIN` 代录，其会话还会被下一次登录踢掉。

**改进方案**

| 步骤 | 内容 |
| --- | --- |
| 1 | **赛前用 API 批量建可写账号**：为每个产业主席团建 `COMPETITION_ADMIN`，以 `allowExtras=true` 授予 `company:manage` + `data:region:edit`；写成一键赛前脚本（幂等，可重复执行） |
| 2 | **按人多开账号**：每名工作人员一个账号，规避单账号单设备约束（不要把"共享账号"当作方案） |
| 3 | **给账号管理界面补"扩展权限"开关**：勾选后前端带 `allowExtras=true`；否则每次都要手工调 API，且界面"编辑"还可能静默清掉手工授予的扩展权限 |
| 4 | **明确公布权限矩阵**：在秩序册里写明"选手可做 X、主席团可做 Y、超管可做 Z"，避免现场临场提权 |

**验收标准**：主席团账号可成功 PATCH 某公司产业字段（200），选手账号同一请求返回 403；两台设备同时用两个账号在线互不影响；账号界面勾选扩展权限后写入生效。

**工作量估计**：0.8 人日（脚本 0.5 + 界面开关 0.3）。

### P0-3 区域经济动力学系统不存在，而它是三套评分中两套的输入

**问题**：见 §1.2。三条公式一条未实现，`Region` 无字段，薪资相关代码零命中。

**为什么是 P0**：Update 3.0 P24 的**经济管理中心评分准则（总分 100）**中，人口发展 15 + 碳排放控制 15 + 就业率 20 + 幸福度 20 = **70 分直接取这四组区域指标**；而 P19 的实体企业评分虽取财报口径，其 Tips 又反复要求企业围绕"幸福度/就业率"优化经营。**区域指标不存在，两套评分都无法计算。**

**改进方案**

| 步骤 | 内容 |
| --- | --- |
| 1 | 为 `Region` 增加指标字段：`population`、`high_quality_talent`、`employment_rate`、`happiness`、`carbon_emission`、`population_capacity`（承载力 k）；均需明确单位与取值范围 |
| 2 | 实现幸福度四因子公式：`C = Q_s/Q_d`、`H = 0.6C + 0.1·log10(P+100) + 2(T/P) + 0.2(E/P)`、`P_sell = P_base·(1+H/100)·(1+(Q_d−Q_s)/Q_d(max))` |
| 3 | 实现人口 logistic 递推：`P(n+1) = min[P(n) + (P(n)·r·H/100 + ΔP_infra)·(1−P(n)/k), k]`，`r=3%` |
| 4 | 实现劳动力薪资：`w = w₀(1+0.9·H/100)(1+k₂·T/P)·ln(P+P₀)`，并接到加工/开采的劳动力成本计算上 |
| 5 | 基建加成的消费方：`Infrastructure` 的 9 项加成按区域加总，作为 `ΔP_infra`、就业率加成、幸福度加成的输入 |
| 6 | 每财年结算时统一递推一次（依赖 P0-6 财年状态机的 `SETTLING` 阶段） |

**必须先裁定**（见 §5.4）：`H` 的定义（"幸福度−100"还是"取值范围 1~100"）、隐性乘法读法（`2(T/P)`）、`SumE`/`SuE` 拼写。

**验收标准**：给定初始人口/基建/供需数据，推进一个财年后人口按公式变化；基建加成能改变区域幸福度与就业率；改动能被评分引擎读取。

**工作量估计**：1.5 人日（字段+公式）+ 0.5 人日（基建加总）+ 0.5 人日（接入结算）。

### P0-4 赛事实际的 4 份数据文件，一行都进不了系统

**问题**：系统的"读表建比赛"功能（`backend/examples/excel/build_from_sheets.py`）**无法消费赛事数据**。

**实测**（运行 `--inspect`）：

| 工作簿 | 工作表名 | 结果 | 退出码 |
| --- | --- | --- | --- |
| `物流里程表.xlsx` | `Sheet1` | 共处理 **0 张表、0 行数据** | **0**（静默） |
| `原料价格.xlsx` | `Sheet1` | 共处理 **0 张表、0 行数据** | **0**（静默） |
| `加工经销配比.xlsx` | `Sheet1`、`Sheet2 (2)` | 共处理 **0 张表、0 行数据** | **0**（静默） |
| `基建影响指标(2).xlsx` | `基建` | 退出码 1（表头含规范外列） | 1 |

静默导入时打印的实际内容：

```
表格来源：…物流里程表.xlsx
比赛名：物流里程表
已处理的工作表：
--- 提示 ---
  · 工作表「Sheet1」不在规范内，已忽略（可选：比赛、财年、股票参数、…、合同类型）
  · 共处理 0 张表、0 行数据（只处理出现在表格里的表，其余表完全不参与产出）
产出资源：
  - 比赛名称与状态              1 条  [competitionMeta]
```

**静默丢弃的数据量**：92（里程表）+ 13（原料价格）+ 70（加工经销配比）= **175 行**，退出码 0；`基建影响指标` 另 32 行**报错**退出。合计 **207 行**赛事核心数据。

**静默失败比报错更危险**：打印了"比赛名：物流里程表"、给出了产出资源、退出码 0 —— 操作人员会认为导入成功。

**逐文件差距**（详见 [`DATA_FIT_REPORT.md`](audit/rules/DATA_FIT_REPORT.md)）：

| --- | --- | --- | --- |

### P0-5 没有"推进财年"这个操作

if prev_status != "ACTIVE" and new_status == "ACTIVE":

| 步骤 | 内容 |
| --- | --- |
| 1 | `FiscalYear` 增加**时间窗口**（`starts_at`/`ends_at`，可空=不设锁）与**阶段** `phase`（`PREPARING/ACTIVE/SETTLING/CLOSED`）；保留 `status` 及其信号语义不变（`phase` 是叠加的第二道门） |
| 2 | 提供判定能力：`current_fiscal_year(cid, at=None)`、`is_within_window(fy, at=None)`、`assert_fiscal_year_writable(cid, at=None)`（越窗/结算中/已关闭抛 **423**）、窗口重叠校验（同比赛不允许重叠，相邻可首尾相接） |

### 3.1 P1-6 / P1-7 详述（股票域，同源）

**(a) 规则规定的定价链**（Update 1.0 P31）：

> 最终股价 = 理论价 × 涨跌幅限制
> 理论价由 4 个因素决定：上轮价、买盘总额、卖盘总额、幸福因子、碳因子

**(b) 系统实现**（`backend/apps/stock/engine.py:167-174`）：

```python
def compute_theoretical(last_close, pressure, drift, max_move_pct):
    """理论价：上轮收盘 × (1 + 压力×maxMovePct + 偏置×maxMovePct)。"""
    return last_close * (1 + pressure * max_move_pct + drift * max_move_pct)
```

`drift = happinessImpact·(幸福度−50)/50 + carbonImpact·碳排偏置`（`engine.py:153-164`），默认 `happinessImpact = carbonImpact = 0.2`（`engine.py:349-350`）。**结构上大体对应**——这部分可接受。

**(c) 但系统额外引入了两个规则外机制**：

1. **AI 做市商**：`generateMarketMakerOrders`（`engine.py:898+`）持续挂双边报价，并**自行建仓/销毁现金**。规则书的股票系统只有玩家买卖双方。
2. **基本面评分偏置 + 随机项**：做市商报价按 `calculate_fundamental_score` 偏移（`engine.py:952-966`），而该评分**包含幸福度**：

```python
# backend/apps/stock/engine.py:800-809
# 3. 幸福度评分：幸福度越高越好
happiness = getattr(stock, 'happiness', None)
if happiness is not None:
    if happiness_float >= 80:  score += 15
    elif happiness_float >= 60: score += 5
    elif happiness_float < 40: score -= 10
```

而规则书用**脚注**特别强调（Update 1.0 P32 脚注 21，逐字）：

> 重点说明：幸福度对股票的影响只有一个渠道——就是通过"幸福因子"影响股价。……**幸福度不会直接影响人口、就业等其他方面，只和股价挂钩。**

系统里幸福度**已经有两个渠道**影响股价：`drift`（合规）与做市商报价偏置（**违规**）。

3. **随机项使赛果不可复现**：

```python
# backend/apps/stock/engine.py:860-862
# 添加随机波动，增加市场不确定性
random_factor = random.uniform(-0.1, 0.1)
score += random_factor
```

**没有随机种子**。同一份输入重放会得到不同股价 —— 赛后无法复算、无法申诉、无法做教学复盘。

**方案**：① 移除做市商报价里的幸福度通道（只保留 `drift`）；② 随机项改为**可配置种子**并从比赛配置读取，使整场比赛可复现；③ 由组委会裁定是否保留 AI 做市商（§5.4），若保留需在秩序册写明；④ 顺带校正涨跌幅口径（默认 `limitPct=0.1` 符合 ±10%，但 `maxMovePct=0.05` 使单轮理论变动上限只有 5%，且有"防连板"逻辑把同侧限幅压到 9.4%、封板时扩到 20% —— 这些规则书未规定，需一并裁定）。

### 3.2 P1-8 补充：收购优先级

规则（Update 1.0 P21-22，逐字）：

> 若某区域对某类产成品的市场需求量为 7000 件，而 A、B 两家经销公司合计拟销售 10000 件（供大于求），则按以下优先级确定收购顺序：**产品等级优先**：产成品等级（评级）更高的公司，优先获得收购资格；**价格竞争优先**：若两家公司产成品等级相同，则启动竞价机制，销售价格更低的公司优先获得收购资格。

系统里没有任何"按等级+价格排序分配有限需求"的实现。`consumer_demands` 只是需求量主数据表。**注意"产成品等级"字段本身也不存在**（见 §5.4 的语义补齐项）。

### 初始价公式与规则书矛盾的补充证据
