## 0. 三个问题与整改优先级

| # | 问题 | 机制一句话 | 现场后果 | 整改类型 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| **C1** | **单线程** | 全部同步视图经 `sync_to_async(thread_sensitive=True)` 走**同一个单线程执行器** | 任一慢请求阻塞全场；财年推进时全场冻结 | 架构/部署 | **高** |
| **C2** | **SQLite 写串行** | 默认回滚日志模式、无 WAL、`busy_timeout=5000`；每写多一条审计 | 写并发一高即 `database is locked` | 配置（+依赖/代码） | **高** |
| **C3** | **心跳与重连放大并发** | 100 客户端 × 20s 心跳 + 断线后全集合扇出重连，nginx 无限流 | Wi-Fi 抖动后上千请求涌向单线程 | 配置 + 前端代码 | 中 |

**三者的关系**：C1 是根因（产能上限=1 个线程），C2 与 C3 是放大器。**只修 C2/C3 而不动 C1，高峰仍会排队**；只修 C1 而不动 C3，新引入的多线程会被瞬时上千请求打满。

## C1 · 全部同步视图共用一个线程

### C1.1 机制（已确认到框架源码）

Django 在 ASGI 下把**同步视图**包进 `sync_to_async(..., thread_sensitive=True)`：

```
backend/.venv/Lib/site-packages/django/core/handlers/base.py
 :129  return sync_to_async(method, thread_sensitive=True)     # 中间件
 :249-250 wrapped_callback = sync_to_async(callback, thread_sensitive=True)   # 视图
 :257-259 / :284-290                                         # 响应渲染
```

`thread_sensitive=True` 的语义是「与任何外层同步线程共用同一个执行器」；在没有外层同步上下文时，**退回一个进程级共享的单线程执行器**：

```
backend/.venv/Lib/site-packages/asgiref/sync.py
 :409  single_thread_executor = ThreadPoolExecutor(max_workers=1)   # 类属性 = 全进程共用
 :462-489   __call__():  thread_sensitive 分支
            :488  executor = self.single_thread_executor           # 无上下文时走这里
```

**关键点**：`single_thread_executor` 是 **`SyncToAsync` 的类属性**（`max_workers=1`），因此**全进程所有同步视图共用这一个线程**，而不是"每个请求一个线程"。

### C1.2 本项目的暴露面

| 事实 | 位置 |
| --- | --- |
| 部署是**单进程 daphne**，systemd 单元无 worker/进程数参数 | `deploy/gipfel.service:26`（`ExecStart=… daphne -b 127.0.0.1 -p 8000 … backend.asgi:application`） |
| ASGI 入口把 HTTP 与 Socket.IO **放在同一进程** | `backend/backend/asgi.py`（`ASGIApp.__call__`：`/socket.io` → socketio，其余 → Django） |
| 项目**没有任何 async 视图**（全仓同步 `APIView`/函数视图） | 各 `apps/*/views.py` |
| 每个请求还有 **14 条中间件**串行执行 | `backend/backend/settings.py:286-305` |
| 其中 `LoginRateLimitMiddleware`、`SnapshotGateMiddleware` 都是自定义同步中间件 | 同上 `:291`、`:294` |
| **每次业务写都额外写一行审计**（同线程、同事务） | `backend/apps/common/signals.py:91-135` → `backend/apps/common/audit.py:63` |
| **每个 4xx/5xx 也写一行审计** | `backend/apps/common/exceptions.py`（`exception_handler` → `log_exception`）→ `audit.py:94` |
| 财年定时器在**请求线程内同步执行**（遍历全公司×全字段 + 逐公司重算计算图） | `backend/apps/competitions/views.py`（创建/状态迁移后调 `_apply_fiscal_year_timer`）→ `apps/company_fields/timer.py` |

### C1.3 实测验证【已复核】

用与 Django ASGI handler 相同的包装方式，并发发起 8 个"同步视图"（各睡 0.2s）：

```
$ backend\.venv\Scripts\python.exe - <<'PY'
import asyncio, threading, time
from asgiref.sync import sync_to_async
seen = []
def work(tag):
    seen.append((tag, threading.get_ident())); time.sleep(0.20)
async def main():
    await asyncio.gather(*[sync_to_async(work, thread_sensitive=True)(f"req{i}") for i in range(8)])
t0 = time.time(); asyncio.run(main())
print("thread ids:", sorted({i for _, i in seen}), "wall: %.2fs" % (time.time() - t0))
PY
```

实测输出：

```
thread ids: [90000]        ← 8 个并发请求全部落在同一个线程
wall: 1.61s                ← 串行（并行应为 ~0.2s）
```

**结论**：**8 个并发请求 = 1 个线程 = 1.61s 串行**。若每个请求耗时 X，则第 N 个请求的等待时间 ≈ N×X。

### C1.4 整改方案（三选一，按改造量排序）

#### 方案 C1-a（推荐落地）：HTTP 与 WebSocket 进程分离 + 多 worker WSGI

**思路**：把"高并发、短请求"的 REST 与"长连接"的 Socket.IO 拆成两组进程。

| 步骤 | 内容 |
| --- | --- |
| 1 | `/api/*` 改为由**多 worker 的 WSGI 服务器**承载（如 `gunicorn -w 4 -k gthread --threads 8`，或 `uwsgi`）。项目已有 `backend/backend/wsgi.py`（`WSGI_APPLICATION` 已配置），无需新增入口 |
| 2 | `/socket.io/*` 继续由 daphne 承载（单独端口，如 `:8001`），nginx 把 `/socket.io/` 反代到它 |
| 3 | nginx 的 `upstream gipfel_django`（现指向 `127.0.0.1:8000`）改指 WSGI 端口；**新增** `/socket.io/` 的 upstream 指向 daphne 端口 |
| 4 | systemd 增加一个 unit（或同一 unit 起两个进程），并给 WSGI 配 `--workers/--threads` |

**必须解决的副作用（关键）**：**实时广播目前是纯进程内的**，多进程后会失效：

```
backend/apps/realtime/gateway.py:54-55   sio = socketio.AsyncServer(async_mode="asgi")   # 无 client_manager
backend/apps/realtime/emit.py:49-57        _seq_lock / _seq_value / _event_ring / _ring_seqs  # 进程内 deque
```

证据：全仓**无 `redis` / `AsyncRedisManager` / 任何 `client_manager`**（`apps/realtime/*.py` 搜索零命中）。因此：

- WSGI worker 里调用的 `emit_resource_changed` **无法把事件推给 daphne 进程里的 socket 连接**；
- 现在之所以能工作，是因为**同进程**：视图用 `asyncio.run_coroutine_threadsafe` 把 `sio.emit` 投递到那个唯一的 event loop（见 `emit.py` 顶部注释）。

**因此方案 C1-a 的必做前置**：引入跨进程事件总线（**推荐 Redis**：`python-socketio[client]` 的 `AsyncRedisManager` 作为 `client_manager`，同时把 `emit` 改为"发布到 Redis"而不是"投递到本进程 loop"）。这会把整改从"改部署"升级为"改代码 + 加依赖"。

> 若现场只有一天且不打算引入 Redis：**不要用 C1-a**，改用 C1-d（缓解项）。

#### 方案 C1-b：把慢操作移出请求线程

| 步骤 | 内容 |
| --- | --- |
| 1 | 财年定时器改为**异步任务**：接口只写"待执行"标记并立即返回，由后台 worker 执行；前端用 Socket.IO 的 `system:progress` 类事件（已存在事件常量）显示进度 |
| 2 | 但**当前无任何任务队列**（全仓无 `celery`/`APScheduler`），需要新引入 |
| 3 | 收益：消除"点一下财年推进 → 全场冻结"这一最痛场景 |

**注意**：Django 5 的原生 `async` 视图可走任意线程池（`thread_sensitive=False`），但项目所有视图都是同步的，且大量使用 ORM 同步调用；**改造成本高于 C1-a**，不推荐在赛前做。

#### 方案 C1-d（赛前兜底，不改代码）：编排规避

- 把财年推进安排在**午休/茶歇**；
- 全场操作错峰（主持人统一口令）；
- 用 `sync_to_async` 之外的线程无关化不可行，故这里只能靠**降低同时请求数**。

### C1.5 验收标准

- [ ] 并发 20 个 `GET /api/companies`（或等价只读接口），**总墙钟时间接近单个请求时间**（而非 20×）；
- [ ] 并发 20 个请求期间，另一个请求的延迟 **< 1s**；
- [ ] 若采用 C1-a：多进程下**实时广播仍能到达其他进程的客户端**（用 2 个浏览器标签 + 1 次写操作验证）；
- [ ] 财年推进请求的响应时间 **< 3s**（或在 C1-b 下立即返回）。

### C1.6 已知的"不该做"

| 做法 | 为什么不行 |
| --- | --- |
| 直接把 daphne `-p` 起多个进程 | Socket.IO 房间状态在各进程内存里，广播与用户房间会错乱；除非有 Redis |
| 只加 `-w` 到 daphne | daphne 不是 WSGI，多进程会争抢同一端口 |
| 给同步视图加 `@async_to_sync` 之类包装 | 不改变 `single_thread_executor` 语义 |
| 依赖 `thread_sensitive=False` 的中间件/视图混用 | 会破坏 Django 的 DB 连接线程亲和性（`async_unsafe`），风险高 |

## C2 · SQLite 写串行且未调优

### C2.1 机制与证据

`DATABASES` 配置**只有一个 ENGINE 与 NAME，没有任何 `OPTIONS`**：

```
backend/backend/settings.py:304-310
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
    }
}
```

> 注：`settings.py:289` 确实有一个 `"OPTIONS"`，但它属于 **`TEMPLATES`**，不是数据库。

实跑 PRAGMA 确认当前生效值【已复核】：

```
journal_mode = delete      ← 回滚日志（非 WAL）
busy_timeout = 5000        ← sqlite3 默认 5 秒（遇锁等待 5s 后抛 "database is locked"）
```

写放大来源：

| 放大器 | 位置 | 说明 |
| --- | --- | --- |
| 每次业务写多一条审计 | `common/signals.py:91-135` → `audit.py:63` | 同事务、同线程 |
| 每个 4xx/5xx 也写审计 | `common/exceptions.py` → `audit.py:94` | 401/403/409 等高频错误全部落库 |
| 审计只增不删 | 无归档命令 | 测试库已 7118 行；两天 100 客户端会到数万行 |

### C2.2 重要更正：`DATABASE_URL` 并未实现

`README.md:29` 声称"环境变量 `DATABASE_URL` 可切换"（生产 PostgreSQL），但实测【已复核】：

| 检查 | 结果 |
| --- | --- |
| `settings.py` 是否读 `DATABASE_URL` / `dj_database_url` | **零命中**（`DATABASES` 硬编码 sqlite3） |
| 全仓 backend Python 是否有 `DATABASE_URL`/`dj_database_url` | **零命中** |
| `requirements.txt` 是否有 postgres 驱动（`psycopg`） | **无** |
| `backend/.env.example` 是否有数据库段 | **无** |

**含义**：**切 PostgreSQL 不是"配一个环境变量"，而是要改代码 + 加依赖 + 建库 + 迁移数据。** 任何依赖"赛前切 Postgres 就行"的计划都不成立。

### C2.3 整改方案

#### 阶段 1（可赛前做，低风险）：SQLite 调优

| 动作 | 具体做法 |
| --- | --- |
| 开 WAL | 在 `settings.py` 加 `"OPTIONS": {"init_command": "PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA busy_timeout=20000;"}`，并在 `apps/common/apps.py` 的 `ready()` 里用 `connection_created` 信号**对每条连接**执行同样 PRAGMA（`init_command` 在部分 Django/SQLite 组合下不生效，需信号兜底） |
| 提高锁等待 | `busy_timeout` 从 5000 → 20000（5s 的等待在高并发下会频繁抛锁错误） |
| 降低写放大 | 审计**批量/异步**化：把 `log_exception` 的 4xx（尤其 401/403）降为**采样写**或只记日志不落库；或把审计写入改为后台队列 |
| 审计归档 | 加一个 management command 归档/清理历史审计（如保留 7 天） |

**验收**：`PRAGMA journal_mode` 返回 `wal`；并发 20 个写请求**不出现** `database is locked`；审计表增长速率下降。

> **注意 WAL 的前提**：WAL 依赖共享内存与文件锁，**必须放在本地磁盘**。若 DB 放在网络盘/NFS/容器挂载卷上，WAL 可能不可用或损坏——部署前必须确认。

#### 阶段 2（若需真正并发）：迁移 PostgreSQL

只有当**多 worker（C1-a）**落地后才有意义（否则单线程下 Postgres 也串行）。需要：

1. `requirements.txt` 加 `psycopg[binary]`；
2. `settings.py` 读 `DATABASE_URL`（或显式分环境配置），并删除 `README.md:29` 的错误声明或把实现补上；
3. 建库 + `migrate` + **数据迁移**（`dumpdata`/`loaddata` 或 `pgloader`）+ 校验行数；
4. 复核所有依赖 SQLite 行为的代码（例如 `select_for_update` 在 SQLite 上静默失效，在 Postgres 上**会真正加锁**——可能暴露此前被掩盖的并发缺陷）。

**验收**：`select_for_update` 路径在高并发下行为正确；`database is locked` 消失。

### C2.4 已知的"不该做"

| 做法 | 为什么不行 |
| --- | --- |
| 用 `cp -a db.sqlite3` 做备份 | 热拷贝正在写入的活库可能拿到损坏副本；项目自己在 `deploy-linux.sh` 里已批评该反模式（应用 `sqlite3 .backup` 或 `.venv` 里的 `snapshot_sqlite_consistent`） |
| 以为"开了 WAL 就能多写" | WAL 仍**只允许一个写者**；它改善的是"读不阻塞写"，不是写并行 |
| 在多进程下继续用 SQLite | 写锁争用会更严重 |

## C3 · 心跳与断线重连放大并发

### C3.1 机制与证据【已读码】

| 事实 | 位置 | 数值/说明 |
| --- | --- | --- |
| 每个客户端每 **20 秒**打一次 `/auth/me` | `frontend/src/stores/auth.ts:166` | `HEARTBEAT_INTERVAL_MS = 20 * 1000` |
| axios 全局超时 **15s** | `frontend/src/api/request.ts:43` | `timeout: 15000` |
| nginx `/api/` 读超时 **120s** | `deploy/nginx-gipfel.conf:55` | `proxy_read_timeout 120s` |
| **Socket.IO 自身还有一条心跳**（独立于 HTTP 心跳） | `backend/apps/realtime/gateway.py:54-59` | `socketio.AsyncServer(..., ping_interval=25, ping_timeout=20)` → 每连接每 25s 一次 ping/pong |
| 断线重连**对每个已加载集合并发补拉** | `frontend/src/api/request.ts:781`，`Promise.all` 在 `:792` | `await Promise.all(cols.map(...))` |
| **产业字段按公司逐个请求**（无合并端点） | `frontend/src/api/request.ts:802` | `/company-fields/${cid}` 在 map 内 → 访问过 N 家公司 = N 个请求 |
| nginx **完全没有限流** | `deploy/nginx-gipfel.conf` | `limit_req` / `limit_conn` 搜索结果**为零** |
| 后端**无全局 HTTP 限流**（只有登录限流） | `README.md:206` 自述；`common/middleware.py` 仅拦 `POST /api/auth/login` | — |
| 同步**写**请求在中间件层也会争用同一线程 | `settings.py:286-305`（14 条中间件） | — |

### C3.2 量化（结构性估算）【待实测】

- **稳态（HTTP）**：100 客户端 × (1/20s) = **5 req/s**，全部排队给同一个线程。
- **稳态（Socket.IO）**：另有每连接 25s 一次的 ping/pong（`ping_interval=25`）。这条走 daphne 的 Socket.IO 分支、**不占那个单线程执行器**，但会与 HTTP 争用同一进程的 event loop 与 nginx 连接池（`keepalive 32`）——**评估并发时不要漏掉它**。
- **重连尖峰**：若每人已加载 10 个集合，其中 5 人访问过 20 家公司详情页 →
  一次重连 ≈ `100×10 + 5×20` = **约 1100 个请求**瞬时涌向单线程。
- 期间任何人的正常操作都在排队；15 秒后前端集体报"请求超时"。
- **注意尖峰的同步性**：Wi-Fi 恢复后所有客户端几乎同时触发对账，**没有退避与抖动**，因此是全量叠加而非摊平。

### C3.3 整改方案

| 层 | 动作 | 效果 |
| --- | --- | --- |
| **前端 · 心跳** | ① `/auth/me` 支持条件请求（`ETag`/`If-None-Match` 或 `updatedAfter` 语义），未变更返回 **304/轻响应**；② 心跳间隔改**自适应**（页面隐藏时拉长到 60s+，活动时 20s） | 直接削掉稳态 5 req/s 的大部分 |
| **Socket.IO ping** | 复核 `ping_interval=25`/`ping_timeout=20` 是否与现场网络匹配：现场 Wi-Fi 抖动 >20s 会导致误判断线并触发重连风暴 | 减少"假掉线"引发的重连 |
| **前端 · 重连** | ① 重连对账加**并发上限**（如同时最多 2 个）；② 加**指数退避 + 抖动**（避免全场同一毫秒一起重连）；③ 产业字段改用**批量端点**（见下） | 把 1100 请求摊平到数秒 |
| **后端 · 批量端点** | 新增 `GET /api/company-fields?companyIds=1,2,3`（或复用既有分页/增量协议）替代逐个 `/company-fields/{cid}` | 请求数从 N 降到 1 |
| **nginx** | 加 `limit_req_zone` + `limit_conn_zone`，对 `/api/` 做速率与连接数兜底（**注意放行 `/api/auth/login` 之外要谨慎，避免误伤正常操作**） | 尖峰时保护后端 |
| **可观测性** | nginx access log 增加 `$request_time`，监控 P95 | 现场能定位长请求 |

> **向后兼容要求**：批量端点必须是**新增**，不能移除逐个端点（老前端/`contract_watcher` 可能依赖）。

### C3.4 验收标准

## 4. 三者的整改顺序与依赖（重要）

```
C2 阶段1（SQLite 调优）
        │  独立、低风险，可先做
        ▼
C3（心跳/重连/限流）
        │  独立，可并行；直接决定 C1 达标后的实际体验
        ▼
C1（并发架构）
        │  改造量最大；若走 C1-a 多进程
        │  → 必须同时引入 Redis 事件总线（否则广播失效）
        │  → 且有 Redis 后，C2 阶段2（Postgres）才有意义
        ▼
C2 阶段2（PostgreSQL）
```

**依赖关系**：

| 关系 | 说明 |
| --- | --- |
| C1-a → Redis → C2 阶段2 | 多进程需要跨进程事件总线；有了 Redis 后再切 Postgres 才能发挥多写并发 |
| C3 → C1 | C3 不解决时，C1 多线程/多进程会被瞬时尖峰打满（只是把排队点后移） |
| C2 阶段1 独立 | SQLite 调优不依赖任何其他项，**建议最先做** |

**建议的最小整改路径**（按投入产出比）：

1. **C2 阶段1**（SQLite WAL + busy_timeout + 审计降噪）——改配置为主，一天内可验证；
2. **C3**（心跳条件请求 + 重连并发上限 + nginx 限流）——前后端小改；
3. 若仍需并发：**C1-a + Redis**，再考虑 **C2 阶段2**。
