# Gipfel 商赛 · 赛务运维分析

> **文档定位**：从**现场办赛**角度（不是代码审计、不是服务器运维）分析这套系统在真实赛事中能不能撑住、哪些流程根本没被实现、开赛前必须补齐什么。
> **与既有资料的关系**：`docs/OPS.md` 讲**服务器运维**（部署/升级/FAQ）；本文件讲**赛务运营**。缺陷取证细节见 [`code_audit/_rules/OPS_READINESS_REPORT.md`](audit/rules/OPS_READINESS_REPORT.md)（28 条就绪度缺陷），本文件是**按时间轴与角色重组的可执行版**，不重复其取证过程。
> **基线**：分支 `bugfix-merged`，VERSION 1.4.0。
> **证据口径**：定性结论为已验证（读码/实跑探针）；**所有人数与耗时均为结构性估算**，须在赛前彩排中实测校准。凡未实测者均标注 `[待实测]`。

## 2. 架构性运维约束（为什么现场会"卡"）

理解这三条，才能理解后面的所有应急预案。

### 2.1 单线程：全部 API 请求排一条队

systemd 单元只有**单进程 daphne**，没有 worker 参数；而**全部 API 视图都是同步视图**，Django 在 ASGI 下用 `sync_to_async(..., thread_sensitive=True)` 包裹 → **所有同步视图共用一个线程**。

**含义**：任何一个慢请求都会阻塞全场。财年定时器（读全公司 × 全字段 + 逐公司重算计算图）在**请求线程内同步执行**，所以"点一下开始新财年"= 全场冻结。

### 2.2 SQLite：写操作串行 + 默认 5 秒锁等待

默认 SQLite 回滚日志模式，未配 `OPTIONS.timeout`、未开 WAL。**每次业务写库还会在同一事务里多插一行审计**，且**每个 4xx/5xx 也插一行审计**。两天 100 客户端会把审计表推到数万行（当前测试库已有 7118 行）。

**含义**：写并发一高就出现 `database is locked`，而返回给学生的只是"请求失败"。

### 2.3 心跳与重连放大了并发

每个客户端每 **20 秒**打一次 `/auth/me`（100 客户端 ≈ 5 req/s 稳态）；axios 全局 **15s 超时**，nginx `proxy_read_timeout 120s`。断线重连时前端**对每个已加载集合并发补拉**，产业字段还**按公司逐个请求**，无并发上限。

**含义**：Wi-Fi 抖动 5 秒后恢复，单次重连可产生约 1100 个请求涌向一个线程 → 全场集体超时。

> **上述三条是结构性推断，未做负载测试** `[待实测]`。赛前必须用真实数据跑一次财年推进并计时。

## 3. 五个硬阻断（任一未解决不建议开赛）

| # | 硬阻断 | 现场表现 | 为什么"流程绕不过" |
| --- | --- | --- | --- |
| **A** | **选手账号只能看，不能做** | 学生笔记本打开系统只能看数据；所有经营动作由主席团代点 | `company:manage`（写字段）、`contract:manage/execute`（签/执行合同）、`data:region:edit`（发需求）**选手默认全部没有**；而唯一能写字段的超管**全网同时只能登录一台设备** |
| **B** | **"推进财年"不是原子操作** | 两个手工按钮、无锁、无状态机；定时器抢不到锁就**静默跳过**；单公司失败被吞 | 7 个时段都依赖它；一次静默失败 = 该财年从错误初值开始，且日志里只有一行 warning |
| **C** | **系统不产出任何财务报表** | 18:30"各代表与审计核对当日账表"无凭据；第二财年贷款要求提交上一财年报表也无法提供 | 系统里只有产业字段的离散值，没有科目/借贷/期初期末/折旧 |
| **D** | **单线程 + SQLite + 无自动备份** | 财年边界与断线重连时大面积超时；断电即两天数据全丢 | 无自动恢复点，文档指向的 `scripts/backup.sh` **在仓库里不存在** |
| **E** | **无评分/排名引擎** | 闭幕式"颁发各产业奖项"没有客观依据；二次选址排序也无依据 | 系统只有股票引擎内部的基本面评分，无公司/机构级评分 |

## 4. 时间轴运维分析（核心）

> 每个阶段给出：**规则要求 → 系统现状 → 现场风险 → 负责人 → 赛前必须准备**。

### 阶段 0 · 赛前 T-7 ～ T-1 天

**规则要求**：Update 2.0 要求参会人员"仔细阅读主办方发出的所有文件"；参会公司至少配备一台笔记本。

**系统现状**：`apps/preparation/` 提供 **39 项准备清单**（质量高，含"为什么需要它/去哪个页面/分几步"），且明确写出最易漏配处（定时器字段、计算图、孤立节点、科技成环、需求指向空产品）。但：

- 清单**全部要求超管权限** → 39 项**只能超管一人做**，无法分派并行；
- 清单是**静态文案**，无负责人/状态/时间点/勾选留痕；
- **没有本次比赛的建包数据**：仓库只有 `demo_competition.py`（通用演示）与 `auto_chain_competition.py`（汽车产业链），与本次"原料/加工/经销/物流 + 金融 + 经管"不匹配；
- 本库实测 `timer_enabled` 字段 = **0**、`contract_field_effects` = **0** → **财年定时器改写字段、合同执行落账这两条最关键的运行期路径从未真正跑过**。

**赛前必须准备（T-7 起）**：

| 序 | 动作 | 验收 |
| --- | --- | --- |
| 1 | 写一个真的 `scripts/backup.sh`（用 `sqlite3 .backup` 或复用 `snapshot_sqlite_consistent`），**验证能恢复** | 删库后能从快照恢复 |
| 2 | 真机部署一次并走完 11 项验证（文档自述"尚未执行"） | 记录 HTTPS/端口/ALLOWED_HOSTS 实际结果 |
| 3 | **写本次比赛的建包数据**（6 类主体，含金融公司与经管中心） | `build_competition --dry-run` + `build_contract_types --check --trial` + 冒烟全绿 |
| 4 | **在真实数据上实测一次财年推进并计时** | 若 >10 秒，把推进安排进茶歇/午休 |
| 5 | 写**角色映射表**（角色→账号→companyScopes→权限） | 见 §5 |
| 6 | 全流程彩排（**至少完整走完一个财年**） | 建合同→填编号→执行落账→看字段变化→推进财年→确认"财年初"定时器生效 |
| 7 | 起 `contract_watcher` 用**独立账号**跑通一家公司记账 + `check()` 平衡校验 | 当天账表有底稿 |
| 8 | 准备纸质合同模板（按类型分批数）+ 编号规则 + 录入分工 | 见 §9 |
| 9 | 打印现场卡片：财年推进 SOP、备份命令、应急回滚、口令交接表 | 见 §8 |

### 阶段 1 · D1 7:30–8:30 签到（高风险）

**规则要求**：入场须出示代表牌，一人一牌，不得转借伪造。

**系统现状**：100 名学生用初始口令首次登录，每次登录 = **bcrypt cost=12 校验 + 顶号写库 + 强制改密再一次 bcrypt 哈希**，全部串行在同一线程；且**同一账号只能一台设备在线**。

**现场风险**：

- 签到 60 分钟内集中登录，单线程下排队明显 `[待实测]`；
- 强制改密期间业务接口返回 401，学生"进不了系统"的主观感受强烈；
- **两人共用账号（或 CFO 与 CEO 各带一台电脑）会互相踢下线** —— 这是最常见的现场纠纷来源。

**负责人**：1 名网络/电源保障 + 1 名账号管理员（超管）。

**赛前必须准备**：① 口令交接表（按公司分发）；② 明确"**一人一号、不得共用**"并提前通知；③ 若某公司确需两台设备，**赛前就为其建两个账号**（不要现场临时处理）；④ 提前 10 分钟开放登录，错峰。

### 阶段 2 · D1 8:40–9:20 开幕式 + 办公室拍卖

**规则要求**（Update 1.0 P6）：价高者得；截至时点未成交的标的**判定流拍**，以**本次拍卖中对应标的的最高有效竞价**为基准定价，**随机分配**给尚未获得办公室的公司；竞得方需在**收到自有运营资金后**按协议支付对价；拍卖合同**一式三份**（两份双方持有，一份留主席团备案）。

**系统现状**：全仓搜 `拍卖`/`auction`/`竞拍`/`流拍` — **零命中**。没有办公室/席位/流拍/候选公司任何模型，**拍卖结果也没有录入入口**。

**现场风险**：这个环节可以纯线下进行（本身可接受），但"最终谁拿到哪间办公室"这件事**没有落进系统**，会直接影响后续的"公司选址/区域归属"，导致系统数据与事实脱节。

**负责人**：主持人（主席团）。

**赛前必须准备**：① 拍卖规则卡与竞价记录表（纸质）；② 流拍后的随机分配过程需**公开可复现**（建议当众抽签并录像）；③ **拍卖结果录入方案**：用公司字段或产业卡片字段承载"办公室编号"，并明确录入人。

### 阶段 3 · D1 9:20–10:50 培训 + BP 评级

**规则要求**：CFO 培训 / 各产业培训 / BP 评级（评级结果影响后续融资等）。

**系统现状**：无 BP 评级模块（全线下）。

**现场风险**：低（纯线下）。但 BP 评级结果若影响合同参数，需明确"评级结果记在哪里"。

**负责人**：各产业主席团。

**赛前必须准备**：BP 评级表 + 结果录入方案（与拍卖同理）。

### 阶段 4 · D1 10:50–12:00 AI 财年（首个体力/系统高峰）

**规则要求**（Update 1.0 P6–P9）：AI 财年内各公司完成**初始选址**、仓库/生产线/劳动力/矿点购置、**公司注册与领取初始运营资金**；选址区域有**容纳上限、先到先得**；选址结果**需公示**（归属经管机构、选址区域、拟开采品类）；签订《选址合同》一式三份。

**系统现状**：

- 区域**没有容纳上限、没有席位模型、没有选址记录**；
- 公司注册所需注册资本、初始运营资金数额在 Update 3.0 有参数，但**无注册流程模型**；
- 贷款、股权投资**均无实体**。

**现场风险**：

1. **超额选址无法判定准入**（无容量上限）→ 只能主席团人工裁决，且事后无法解释；
2. **"先到先得"没有时间戳依据** → 争议无解；
3. 所有购置动作只能靠**改产业卡片数字字段**近似表达，**没有资产归属** → 后续"抵押贷款/折旧"全部无基础。

**负责人**：各产业主席团 + 1 名经管主席团。

**赛前必须准备**：① **每个区域的容纳上限表**（纸质+系统字段）；② 选址登记表（公司/区域/时间戳/顺序号，建议现场用纸记录并录像）；③ 明确"席位先到先得的判定依据"（建议以**纸质登记时间**为准，而非系统时间）；④ 购置动作的字段映射表（买一台生产线改哪个字段）。

### 阶段 5 · D1 14:15–16:00 第一财年（首次全量并发）

**规则要求**：各产业正常经营；碳排放按"碳排系数 × 产量"核算；超额需缴超标费或购买碳配额。

**系统现状**：经营靠产业字段（现金/库存/配额/碳排等，约 11 个非计算字段/公司）；合同 DSL 可表达业务规则，但**需要主席团现场建合同**。

**现场风险**：

| 风险 | 说明 |
| --- | --- |
| **数据录入量** | 按"4~6 个产业 × 6~8 家公司 ≈ 30~40 家、每家约 11 个字段"估算，**400+ 个字段值**需录入。若选手不能写，只能主席团代录，**105 分钟窗口内很可能填不完** |
| **首次并发** | 全场同时操作，单线程 + SQLite 首次承压 |
| **碳排无配额市场** | 规则要求"碳交易市场购买碳配额抵消超额"，**系统无碳配额与交易模块** |

**负责人**：各产业主席团（录入）+ 主持人（控时）。

**赛前必须准备**：① **字段映射表**（每家公司、每个字段的初值口径）；② 若选手无写权限，**按产业分工录入**并把录入量算进彩排；③ 碳排超标现场计算表（Excel 兜底）。

### 阶段 6 · D1 16:40–18:30 第二财年（+ 贷款开放）

**规则要求**（Update 1.0 P8）：**第 2 财年起开放贷款**；需提供**上一财年财务报表（资产负债表/利润表/现金流量表）**；抵押资产评估价 ≤ 贷款额度 70%；年利率由主席团规定；利息 = 本金 × 年利率 × 实际期限；逾期强制划扣 + 抵押物处置。

**系统现状**：**贷款全链缺失**（无贷款实体、无利息计算、无抵押评估、无逾期处置）；**财报不存在** → "提交上一财年报表"这一前置条件无法满足。

**现场风险**：贷款环节**只能全线下**（纸质申请 + 人工核算）。若用人工算利息，**必须统一口径**（如"按财年整期计算"）并留底稿。

**负责人**：金融公司/经管主席团 + 审计。

**赛前必须准备**：① 贷款申请表 + 利率与期限口径卡；② **利息计算模板**（Excel，含逾期处置规则）；③ 抵押物清单与评估价（第三方评估机构角色需人担任）。

### 阶段 7 · D1 18:30–19:40 当日收尾 + 对账（P0 缺口）

**规则要求**：各代表与审计核对当日账表后打扫卫生。

**系统现状**：**不产生任何会计意义上的报表**，也没有按公司导出账目的能力（唯一导出是准备归档 markdown/JSON，且需超管）。系统里只有离散字段值（当前测试库 104 行 / 12 家公司）。

**唯一可用的兜底路径**：`contract_watcher/bookkeeping_example/` 是一套 12 张表的真实账套（银行流水账/明细账汇总/资产负债表/利润表/现金流量表等），由 `shang.py` 通过 **xlwings 驱动本机 Excel** 写入，自带平衡校验 `check()`。**这是本系统里唯一真正好用的"对账底稿"工具**，但有前提与冲突：

- 需要 **Windows + 已装 Excel + `pip install xlwings`**；
- **每家公司一本** `books/company_<id>.xlsx`，由**单进程串行**写（单实例锁）；
- 记账规则**要人手写 Python**（`handlers.py` 里实现 `handle_<key>_passed`）；
- **只覆盖账号 `companyScopes` 范围内的公司** → 4 个产业需按产业开多个账号 + 多份数据目录；
- ⚠️ **致命冲突**：它启动时会登录，而**登录即递增 `token_version` 并踢掉同账号所有旧会话**；401 时还会自动重登 → **若与组委会浏览器共用账号，双方会互相顶号、无限循环**（每轮一次 bcrypt + 一次写库）。**必须给它专属账号，且不与任何人共用。**

**现场风险**：审计拿到的是"学生自己记的 Excel + 一个学生自己写的记账脚本"，**系统字段值与手上账表没有任何自动比对**。

**负责人**：记账/审计（独立账号）。

**赛前必须准备**：① 提前跑通 watcher 记账 + `check()` 平衡；② 确定"当天账表"的正式载体（建议：watcher 产出的 Excel + 纸质签字）；③ 明确"以纸质为准"的裁定规则。

### 阶段 8 · D2 8:30–17:15 第三～第六财年

**规则要求**：第三～第六财年正常经营；**第 4 财年提交研发合同 → 第 5 财年才能生产**（研发前置、生产后置，不可即时研发即时生产）。

**系统现状**：无跨财年门禁（`FiscalYear` 无阶段字段），研发/科技树靠 `tech_tree` 配置 + 人工判断。

**现场风险**：

- 跨财年门禁**只能人工守**（主席团记住"第 4 财年研发的品类第 5 财年才能生产"）；
- 生产设备/生产线有"单财年产能上限"（如加工产线三级 2400 件、生产设备三级 400 件），**系统无产能上限校验** → 超额生产靠人工核。

**负责人**：各产业主席团。

**赛前必须准备**：产能上限表 + 研发-生产对应表（纸质卡片，每产业一张）。

### 阶段 9 · D2 17:15–18:20 终局固化 + 闭幕式准备

**规则要求**：整理各公司资料，准备闭幕式。

**系统现状**：**无任何业务数据的 Excel/CSV 导出** → 闭幕式颁奖数据要手抄。

**现场风险**：30 分钟内要固化的数据量很大（30~40 家公司 × 多个字段），手抄几乎不可能及时完成。

**负责人**：超管操作员。

**赛前必须准备**：① **终局数据模板**（按公司/产业预置的 Excel，现场填）；② 或赛前请开发提供"数据导出"能力（`preparation` 导出不够用，它只含准备数据）；③ 明确的**截止时点**（如 17:15 后一律不接受数据修改）。

### 阶段 10 · D2 18:30–19:00 闭幕式颁奖（P0 缺口）

**规则要求**：颁发各产业奖项。

**系统现状**：**无评分与排名引擎**。Update 3.0 给出三套评分准则（实体企业/金融公司/经管中心），但：

- 实体企业评分指标全部取自财报 → **系统无财报**；
- 经管中心评分 70 分取自区域指标（人口/碳排/就业率/幸福度）→ **系统无区域指标字段**；
- **金融公司评分准则一节在 PDF 中根本不存在**（目录书签损坏为"错误!未定义书签。"）。

**现场风险**：**奖项无法客观产出**，只能在闭幕式现场人工测算 → 时间压力极大且易出错。

**负责人**：组委会 + 主席团。

**赛前必须准备**：① **人工评分模板（必须赛前做好并彩排）**；② 各指标的数据来源与责任人；③ 前文所述"八财年 vs 赛程 6 财年"等口径必须**提前裁定**，否则现场算不出分。

## 5. 角色映射与账号方案

### 5.1 系统只有 3 个角色，真实赛务有 6+ 种

| 真实角色 | 系统对应 | 缺口 |
| --- | --- | --- |
| **主席团**（原料/加工/经销/物流/金融/经管，共约 6 个） | `COMPETITION_ADMIN` | 无**产业维度隔离**（`companyScopes` 只能按公司勾选）；所有比赛管理员权限完全相同 |
| **审计** | 无 | **无"只读审计"账号**；`COMPETITION_ADMIN` 默认同时持有 `contract:manage` + `contract:execute`（能建能执行）→ **审计与执行无职责分离**；且 `GET /api/audit-logs` 需超管 → **审计看不到审计日志** |
| **消费者（市场）** | 无 | 需求发布需 `data:region:edit`，属扩展集，**界面授不出去** |
| **第三方资产评估机构** | 无 | **无模型、无页面、无角色** |
| **组委会/秘书长/会务** | 无 | 公告只支持"版本更新公告"；消息中心可群发但无公文 |
| **主持人** | 无 | 无计时器、无大屏、无定向广播房间 |

### 5.2 账号管理的三个硬限制（现场必须知道）

1. **角色下拉只有三项**（超级管理员/管理员/参赛选手）；
2. **没有权限勾选框** —— 权限由 `derivePermissions(role, companies)` **硬编码派生**，界面上无法给"消费者"加 `data:region:edit`；
3. ⚠️ **界面保存会静默清掉手工授的权限**：编辑账号保存时固定提交派生权限。**只要有人事后在界面上"编辑"过一次该账号，之前用 API 授的扩展权限就被删除，而且没有任何提示。**

### 5.3 推荐账号方案（不改代码）

| 账号 | 角色 | 附加权限（API 授，`allowExtras: true`） | 用途 |
| --- | --- | --- | --- |
| `admin` | SUPER_ADMIN | 隐式全权 | **唯一**：财年推进 / 账号 / 数据管理 / 终局导出。**固定一台设备，不换人换设备** |
| `chair-material` 等 ×6 | COMPETITION_ADMIN | `company:manage`、`data:region:edit` | 各产业主席团：填本产业字段、建/执行合同、发需求 |
| `audit01` | COMPETITION_ADMIN | 仅默认集（**不额外授予**） | 审计：核对账表（只读合同+编号） |
| `watcher` | COMPETITION_ADMIN | 不额外授予 | **专属**给 `contract_watcher`，不与任何人共用 |
| 学生账号 | PLAYER | 无（默认只读） | 查看数据、看本公司合同、股票下单 |

**铁律**：① 上表所有用 API 授过扩展权限的账号，**在纸质映射表上打印"禁止在账号管理界面点『编辑』保存"**；② 超管会话同一时刻只能一台设备，**必须在交接表上写明谁持机**。

### 5.4 最小人员配置（保守估算）

| 角色 | 人数 | 缺席后果 |
| --- | --- | --- |
| 超管操作员 | 1 | **比赛直接停摆**（"比赛管理"页仅超管可见，没人能推进财年），且无 B 角可接手 |
| 产业主席团 | 6（原料/加工/经销/物流/金融/经管） | 该产业字段与合同无人能写 |
| 记账/审计 | 1 | 当天账表没有底稿，18:30 无法核对 |
| 主持人 | 1 | 时间盒失控、无广播 |
| 网络/电源保障 | 1 | 故障无法即时处置 |
| **合计** | **≈ 10–12 人** | |

## 6. 财年推进 SOP（现场最重要的一张卡）

### 6.1 为什么需要 SOP

"推进财年"在系统里是**两个互不相关的手工动作**（"结束财年" PATCH + "开始新财年" POST），**没有事务、没有锁、没有状态机、没有幂等保护**。已知失效模式：

| 失效模式 | 触发 | 后果 |
| --- | --- | --- |
| **两个 ACTIVE 财年** | 两台设备/两个标签页同时点"开始新财年"（后端不检查是否已存在 ACTIVE） | 前端只显示年份较大的那个，旧的那个永远显示"进行中" |
| **FY_START 静默跳过** | 上一个 FY_END 定时器还在跑（前端 15s 已放弃，服务端还在继续） | **所有公司"财年初"重置值一个都没写入**，日志只有一行 warning |
| **部分公司未重置** | 单公司定时器异常 | 界面显示"财年已开始"，实际部分公司/字段未改写，**无法从界面看出哪家失败** |
| **回切重置全场** | 把 CLOSED 再 PATCH 成 ACTIVE | **再触发一次 FY_START**，全场字段被再重置一遍 |

### 6.2 SOP 卡（建议打印贴在主席台）

```
【财年推进 SOP】  固定 1 人操作，固定 1 台设备
① 确认全场已停止操作（主持人喊停），等待 30 秒
② 记录当前快照：跑一次 backup.sh，记下文件名与时间
③ 点【结束财年】→ 等界面刷新完成（不要连点）
④ 看第二屏日志：确认出现 "FY_END" 且无 "已在执行中，跳过本次并发触发"
⑤ 等 30 秒（等 FY_END 定时器真正结束）
⑥ 点【开始新财年】→ 等界面刷新
⑦ 校验：打开「设置→比赛准备总览」，确认字段值已变化（抽 2 家公司）
⑧ 若第 ⑦ 步没变化 → 看日志是否"跳过"；确认上一轮结束后，再 PATCH 一次 status（先 CLOSED 再 ACTIVE 可重触发，但会重置全场字段，慎用）
⑨ 主持人宣布新财年开始
```

**时序建议**：把推进安排在 **12:00–14:00 午休** 或 **16:00–16:30 / 17:15–17:45 茶歇**，**不要**在整点开赛时刻。

### 6.3 二次校验点

- 每个财年结束后，**人工核对该财年的字段初值**（建议抽 2 家公司、每公司 3 个字段）；
- 若出现两个 ACTIVE 财年：**立刻把年份小的那个 PATCH 成 CLOSED**（不要点两次"结束财年"）。

## 7. 备份与灾难恢复

### 7.1 现状（P0）

- 生产环境**没有定时备份、没有 systemd timer、没有 cron**；
- 文档指向的 `scripts/backup.sh` **在仓库里不存在**（`docs/MIGRATION.md` 让你自己写，且示例用 `cp -a` **热拷贝正在写入的活库** —— 正是本项目自己批评过的反模式）；
- **没有"每个财年前自动快照"**：两天 7 个时段，可恢复点实际上只有"上次部署"。

### 7.2 赛前必须做

| 动作 | 命令要点 |
| --- | --- |
| 写 `backup.sh` | 用 `sqlite3 db.sqlite3 ".backup '<目标>'"`（**不要** `cp` 活库）或复用 `scripts/lib/deploy-common.sh` 的 `snapshot_sqlite_consistent` |
| 验证恢复 | 在另一台机器上恢复并启动，确认数据完整 |
| 备份策略 | **每个财年开始前 + 每天收尾后**各一次；同时拷到 **U 盘 + 第二台机器** |
| 贴卡 | 把 `db.sqlite3` 与 `uploads/` 的路径、备份命令打印贴在服务器旁 |

### 7.3 现场执行清单（7 次快照）

| 时点 | 动作 |
| --- | --- |
| 开赛前 7:00 | 快照 A0（原始状态） |
| 每财年开始前 | 快照 A1–A7（共 7 次，每次约 30 秒） |
| D1 18:30 / D2 18:20 | 收尾快照（赛后归档用） |

### 7.4 断电/服务挂的恢复顺序

```
① 确认最近快照文件名
② systemctl stop gipfel
③ 用快照覆盖 db.sqlite3（若快照是 .backup 产物直接替换文件）
④ systemctl start gipfel
⑤ curl /api/health 健康检查
⑥ 让超管登录，确认财年状态与字段值
⑦ 主持人向全场宣布"当前财年重新开始"或"从快照时点继续"
```

## 8. 现场应急卡（一页纸）

| 症状 | 现场动作 | 不要做 |
| --- | --- | --- |
| **全场页面转圈 / 大量"请求超时"** | 等待 1–2 分钟；确认是否有人正在推进财年；看 access log 是否有长请求 | **不要连点第二次** |
| **`database is locked`** | 停止一切写操作 60 秒；关掉多余标签页；必要时 `systemctl restart gipfel`（systemd 3 秒自愈） | 不要反复重启 |
| **财年推进后字段没变** | 看日志是否"财年定时器：…已在执行中，跳过本次并发触发" → 等上一轮结束再重新 PATCH 一次 | 不要立即再点"开始新财年" |
| **出现两个"进行中"财年** | 立刻把年份小的那个 PATCH 成 CLOSED | 不要点两次"结束财年" |
| **服务起不来** | 恢复最近快照 → `systemctl restart` → `curl /api/health` | 不要在现场做代码升级 |
| **怀疑选手改数** | 系统**查不到字段变更**（字段值改动不进审计）→ 只能靠 `contract_watcher` 的 `records/*_readable.json` 与纸质合同比对；**当场以纸质为准** | 不要指望系统举证 |
| **学生说"被踢下线"** | 确认是否账号共用（一人一号铁律）；为其新建第二个账号 | 不要共用账号 |
| **版本硬封锁（白屏/要求刷新）** | 让学生 `Ctrl+Shift+R` 硬刷新 | **午休不要做升级/热修** |
| **超管被顶号** | 确认是否有第二个设备用了同一账号（含 watcher） | 不要让 watcher 用超管账号 |

## 9. 纸质交付物与编号规则

规则反复要求纸质合同：办公室拍卖**一式三份**、生产资料购买**一式三份**、原料购销**一式四份**、三方物流**一式六份**、借款合同**一式两份**、股权投资协议**一式四份**、定向拨款协议**一式四份**。

**系统现状**：**不打印、不导出、不生成任何合同文档**；没有"份数"概念；系统里只有"合同实例"（参与方+输入项+效果），**没有可签署的合同正文**；`signed_at` 是点击执行时服务端自动打的时间戳，**与纸上签字无关**。

**唯一的连接点**：各参与方手填的 `contractNumber` —— 而它**没有校验、没有唯一性约束、没有纸质模板**；且编号补全的范围校验对持 `contract:manage/execute` 的账号**直接放行** → **任何主席团成员都能替别家公司的合同填编号**（本应各公司自填自己那份）。

**赛前必须准备（三件套）**：

| 项 | 内容 |
| --- | --- |
| **模板** | 按合同类型准备纸质模板，**标注份数**（2/3/4/6 份）与签署栏（含"经济管理机构对应的主席团"备案份） |
| **编号规则** | 建议 `产业-财年-序号`（如 `MAT-F1-007`），**唯一性由人工登记表保证**；明确"谁在系统里录入编号" |
| **录入分工** | 明确"各公司自填自己那份"的执行方式，并**在系统里抽查**是否有越范围填号 |

**U 盘 / 赛后归档**：系统没有任何"把业务数据带出去"的能力（无 Excel/CSV 导出）。学生只能用 U 盘互拷自己的 Excel 账本。组委会若要在闭幕式前用系统导出"各公司最终经营数据"，**目前做不到**。

## 10. 规则中的非技术合规点（赛务需执行）

这些是 Update 2.0 的**纪律与安全要求**，系统不参与，但赛务必须落实：

| 项 | 要求 | 落实动作 |
| --- | --- | --- |
| **代表牌** | 出入场地须出示；仅限本人，不得转借、伪造（违者取消资格）；严格执行**一人一牌** | 签到台核验 + 巡查 |
| **午休外出** | 食品安全与往返人身财产安全**责任自负**；超出规定返回时间未入场者需**组委会书面审批**，否则视为自动放弃 | 准备书面审批单 + 返场签到 |
| **提前离场/迟到** | 须提前联系秘书长并说明理由；非规定时间离开须向秘书长/会务报备 | 报备登记表 |
| **晚间安全** | 回家须家长接送；**每晚安全到家后以公司为单位统一向秘书长报备** | 按公司收报备（建议群内接龙留痕） |
| **卫生** | 每日结束清理所在区域（桌面/地面/垃圾），经组委会检查合格方可离场；检查组不定时巡查，情节严重取消资格 | 检查表 + 合格签认 |
| **纪律巡查** | 组委会成立**专项观察团**全程巡查；不当行为（寻衅滋事/恶意冲突/扰乱秩序）立即取消资格并追责 | 观察团排班 |
| **着装** | 不得奇装异服，入场须穿着合适 | 签到台把关 |
| **自带物品** | 笔记本电脑（每公司至少一台）、手机、计算器、U 盘、插线板 | 赛前通知 + 现场备用 |
| **诚信/防作弊** | 不得数据造假、恶意竞争；一经发现取消资格并公示 | 见 §11 举证方案 |

## 11. 防作弊与事后举证

**规则**："不得有任何作弊行为（如数据造假、恶意竞争等），一经发现，立即取消参会资格并进行公示。"

### 11.1 能用的（应当依赖）

- **合同执行是原子的且留痕**：先原子抢占 `EXECUTED` 再落账，重复执行返回 400；执行后显式补写审计（含落账字段摘要）；
- **每次合同落账写一行不可变的 `ContractFieldEffect`**（`op/value_raw/before_raw/after_raw`）→ **可事件溯源复原**；
- **股票推进轮次**有进程内锁 + 409 + 整轮事务；
- **`contract_watcher`** 把每份通过合同翻译成中文可读记录（`records/<key>/contract_<id>_..._readable.json`，含参与方/填写内容/前置检查/落账明细）→ **这是本系统里唯一真正好用的赛后取证工具**。

### 11.2 不能用的（缺口）

| 缺口 | 后果 |
| --- | --- |
| **公司字段值改动完全不落审计**（`MODEL_TO_RESOURCE["CompanyFieldValue"] = None`，信号跳过） | **现金、库存、配额、碳排这些真正会被造假的数字，谁在何时从 X 改成 Y，系统里查不到** |
| **审计日志只有超管能看**，且只支持按 `kind/model/operatorId/competitionId` 过滤，**没有按公司/时间段查询** | "查一下 A 公司今天的现金变动"**做不到** |
| **审计日志只增不删**（当前测试库已 7118 行），两天会到数万行，无归档命令 | 列表越来越慢 |
| **纸质合同与系统记录只有手抄编号这一条细线**，无校验、无唯一约束 | 造假难举证 |

### 11.3 现场取证方案（在系统补齐前）

1. **以纸质为准**：赛前明确"合同编号与签署以纸质原件为最终依据"；
2. **双录**：关键环节（拍卖、选址、二次选址、大额合同）**录像 + 拍照留档**；
3. **对账留痕**：每天 18:30 由审计与公司代表**双签**纸质账表；
4. **抽查机制**：每天随机抽 2–3 家公司，用 `contract_watcher` 的可读记录与纸质合同核对；
5. **关键数字快照**：每个财年开始前导出一次字段值清单（用快照文件），可对比"财年内的变化"。

## 12. 可观测性与故障定位

| 需要盯的 | 位置 / 方法 |
| --- | --- |
| 应用日志 | `backend/logs/gipfel.log`，第二块屏 `tail -f` |
| **重点看三类日志** | ① `财年定时器`（是否有"跳过"）② `审计写入失败` ③ `database is locked` |
| 健康检查 | `docs/OPS.md` §5 的 5 条 `curl`（`/api/health` 等） |
| 访问日志 | nginx access log：找长请求与 4xx/5xx 尖峰 |
| 版本一致性 | 任何升级后 `VERSION.json` 必须与 `/api/version` 一致，否则**全客户端被硬封锁** |
| 数据库锁定 | 出现 `database is locked` 说明写并发超限，立即降载 |

**注意**：服务靠 systemd `Restart=always` 自愈（3 秒），但**没有健康检查/告警** → **进程崩过现场没人会知道**，必须靠人盯日志。

## 14. 结论与开赛判据

### 14.1 一句话结论

**以当前状态开赛，比赛不会"崩溃"，但会在第一个财年就瘫痪 —— 因为根本没人在系统里干活。** 系统是一套做得很扎实的**管理端**（准备清单 39 项、合同 DSL、股票撮合、审计日志、Excel 建包、归档导入导出、外部记账监听），却被设计成**由主办方操作的教务系统**，而真实比赛要求**选手在自己的笔记本上完成经营动作**——这两者在权限模型上冲突。

### 14.2 可开赛的最低判据

以下 **5 条全部满足**才建议开赛：

- [ ] **A** 选手/主席团能被写入系统：赛前用 API 为 6 个主席团建 `COMPETITION_ADMIN` 并授 `company:manage`/`data:region:edit`，且映射表已打印"禁止界面编辑"
- [ ] **B** 财年推进 SOP 已演练，且在真实数据上**实测过推进耗时**（若 >10 秒已改到茶歇执行）
- [ ] **C** 对账兜底已就绪：`contract_watcher` 用独立账号跑通，当天账表有底稿，且明确"以纸质为准"
- [ ] **D** `backup.sh` 已写好并**验证过恢复**；7 次快照的执行人与时点已排定
- [ ] **E** 人工评分模板已做好并彩排过，"八财年 vs 6 财年"等口径已裁定

### 14.3 若以上任一条无法满足

**建议缩减赛程或降级为线下**：把系统当"看板 + 合同留痕"，把资金/资产/评分全部改为纸质流程，并明确告知参赛代表。**强行用系统跑完整流程，风险是"数据与事实不一致且无法举证"。**
