### [P2] O5-01 无域名（纯 IP）部署与「升级脚本引导的实例」从不写 `CORS_ORIGIN`，Socket.IO 的 `cors_allowed_origins` 退化为 `"*"`，而文档宣称未配置时「仅限开发/私网反射」

- **证据**：
  - `scripts/deploy-linux.sh:234` `if [[ -n "$DOMAIN" ]]; then` —— `CORS_ORIGIN` 的写入（`:236`、`:238`）完全位于该分支内，**无域名时整段跳过**；`else` 分支（`:243` 起）只处理日志查看器地址，不写 `CORS_ORIGIN`。
  - `scripts/update-from-github.sh`：全脚本 **0 处** `CORS_ORIGIN`（`git grep -n "CORS_ORIGIN" master -- scripts/update-from-github.sh` 无输出），但 `:223` 却 `warn "已生成 .env；公网访问入口（DJANGO_ALLOWED_HOSTS/CORS/CSRF）将在下方自愈块按域名/公网 IP 补全"` —— 该承诺对 CORS 不成立（自愈块 `:324-354` 只写 `DJANGO_ALLOWED_HOSTS`）。
  - `backend/apps/realtime/gateway.py:39-51`：`raw = getattr(settings, "CORS_ORIGIN", "") or ""` → `if not raw: … return "*"`；`:54-56` 在**模块导入时**就把结果传给 `socketio.AsyncServer(cors_allowed_origins=…)`（静态列表，运行期不再变）。
  - `backend/.env.example:55` `# CORS_ORIGIN="https://your-domain.com"` 默认注释 ⇒ 默认未配置。
  - `deploy/README.md:201` 宣称：「`cors_allowed_origins` 不再硬编码 `*`，改为复用主后端同一份 `CORS_ORIGIN` 白名单（**未配置时退化为 `*`，仅限开发/私网反射**）」——后半句不成立：socket.io 的 `"*"` 是**放行任意 Origin**，不存在私网限制（私网限制只存在于 HTTP 层 `cors_origin_validator` → `is_local_or_private_origin`）。
- **现状**：HTTP 层的 CORS 未配置时会走 `is_local_or_private_origin` 动态反射（确有私网限制）；但 **WebSocket 层是另一套实现**，未配置时直接返回 `"*"`。部署脚本只在传了 `--domain` 时才写 `CORS_ORIGIN`。
- **运维影响**：默认（纯 IP）部署形态下，任意第三方站点的页面都能从浏览器向本实例发起跨域 Socket.IO 连接；`connect` 仍校验 JWT（`gateway.py:8`、`:63-79`），而前端 token 存在同源 storage 中、跨域脚本读不到，因此**不构成越权读取**，主要后果是：① 唯一的跨站防线（Origin 白名单）在默认形态下等于没有；② 任意站点可对本实例发起未认证 WebSocket 连接洪泛（配合 nginx `/socket.io/` 的 `proxy_read_timeout 86400s`、每连接长占，见 O3 域）。等级定为 P2 而非 P1 正是基于「连接后仍需有效 JWT」这一约束。
- **命中形态**：纯 IP 部署（`--install-dir /opt/gipfel --with-nginx`，不带 `--domain`）**必中**；任何由 `update-from-github.sh` 首次引导出 `.env` 的实例（含带 `--domain`）**必中**；`deploy-linux.sh --domain` 首次部署不中。
- **验证命令**：
  ```bash
  git grep -n "CORS_ORIGIN" master -- scripts/            # 只命中 deploy-linux.sh，且都在 DOMAIN 分支内
  git show master:backend/apps/realtime/gateway.py | sed -n '39,51p'
  git show master:deploy/README.md | sed -n '201p'
  ```
- **既有审计重叠**：无（U14 X 系列未涉及 CORS_ORIGIN 的部署侧写入条件）。
- **建议方向**：部署/升级脚本无论是否有域名都显式写入 `CORS_ORIGIN`（纯 IP 形态写 `http://<公网IP>` 与 `http://<IP>:<LV_PORT>`）；或让 `_socketio_cors_origins()` 在未配置时返回空列表（拒绝跨域）而非 `"*"`，并同步修正 `deploy/README.md:201` 的表述。

### [P2] O5-02 有域名但未执行 certbot（即模板默认产物）时，「日志查看器」入口被硬编码为 `https://log.<host>/`，而 443 端口无任何监听

- **证据**：
  - `backend/apps/auth/views.py:101-113`：`log_viewer_url = os.environ.get("LOG_VIEWER_PUBLIC_URL", "").strip()`；为空时按 Host 推导，非 IP 字面量分支 `:110-111` 直接 `log_viewer_url = f"https://log.{host}/"` —— **不看 scheme、不看是否启用 TLS**。
  - `deploy/nginx-gipfel.conf:303-392`：整段 443/HSTS 模板处于**注释态**（`# === NGINX_SSL_443_START ===` 起）；默认渲染产物只有 `listen 80`（`:16-17`）与日志查看器块（`:186`/`:242`）。
  - `deploy/README.md:108` 让用户「# 浏览器打开 https://comp.example.com」，而 `:122` 自述「未启用 HTTPS 时以 HTTP(80) 提供，功能正常」；`:193-199` 把 certbot 定位为推荐但**可选**的人工步骤。
- **现状**：`deploy-linux.sh --domain X --with-nginx` 的默认产物是「80 端口明文站 + 日志查看器 `log.X:80`」。此时 `LOG_VIEWER_PUBLIC_URL` 不会被写入（该变量仅无域名分支处理，见 O5-07），因此走 Host 推导分支 → 生成 `https://log.X/`。
- **运维影响**：超管在前端点「系统设置 → 日志查看器」时，浏览器打开的是 `https://log.X/`，而服务器 443 无监听 → 入口 100% 打不开（连接被拒/超时）。运维若按文档「可选」跳过 certbot，就会得到一个"文档说可用、实际不可用"的功能入口；排查方向还会被误导向 DNS/令牌/密钥（OPS.md Q8 列了 5 条排查项，唯独没有"443 未监听且 URL 被硬编码为 https"）。附带影响：DNS 也必须存在 `log.X` 的 A 记录，否则连 certbot 都签不下来。
- **命中形态**：`--domain` 首次部署 + 未跑 certbot = **必中**；纯 IP 部署不中（走 `http://<IP>:<port>/`，`:108-109`）。
- **验证命令**：
  ```bash
  git show master:backend/apps/auth/views.py | sed -n '101,113p'
  git show master:deploy/nginx-gipfel.conf | sed -n '303,311p'   # 全为注释
  git show master:deploy/README.md | sed -n '108p;122p'
  ```
- **既有审计重叠**：无。
- **建议方向**：按实际访问 scheme 推导（`request.is_secure()` 需先补 `SECURE_PROXY_SSL_HEADER`，见 O5-03）；或在 `--domain` 分支也写 `LOG_VIEWER_PUBLIC_URL`，并在未启用 HTTPS 时写 `http://log.X/`；或在部署收尾把「是否已启用 443」的结论显示给运维。

### [P2] O5-03 主后端完全没有 `SECURE_PROXY_SSL_HEADER` / `*_COOKIE_SECURE` / `SECURE_HSTS_*`，而同仓日志查看器具备——nginx 终止 TLS 后主后端仍认为自己是 HTTP

- **证据**：
  - `backend/backend/settings.py:461-463` 是该文件最后三行，仅 `SESSION_COOKIE_HTTPONLY = True`、`CSRF_COOKIE_HTTPONLY = True`；`git grep -n "SECURE_" master -- backend/backend/settings.py` **无输出**（连同 `USE_X_FORWARDED_HOST` 也缺失）。
  - `backend/logviewer/logviewer/settings.py:53` `SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")`；`:59-64` 按 `LOG_VIEWER_PUBLIC_URL` scheme 决定 `SESSION_COOKIE_SECURE = CSRF_COOKIE_SECURE`。
  - `deploy/nginx-gipfel.conf:53` 主站点 `/api/` 已传 `proxy_set_header X-Forwarded-Proto $scheme`——头传了，但主后端不消费。
- **现状**：两个 Django 站点共用一套反代与一份 `.env`，但安全设置不对称：日志查看器识别 `X-Forwarded-Proto` 并按 scheme 决定 Secure cookie；主后端既不识别，也没有 HSTS / HTTPS 跳转 / Secure cookie / `SECURE_CONTENT_TYPE_NOSNIFF` 等任何一项。
- **运维影响**：启用 HTTPS（certbot 终止 TLS、回源为明文 HTTP）后，主后端内 `request.is_secure()` 恒为 `False`，`request.scheme` 恒为 `http`：① 主站 `csrftoken`/`sessionid`（`/admin` 登录使用）不会带 `Secure`，同域 HTTP 泄露即可被复用；② 任何以 scheme 为条件的逻辑（当前是 `views.py:101-113` 的地址推导，未来还会有重定向/回调）在 HTTPS 下判断错误；③ 仓库从未在任何流程里跑 `manage.py check --deploy`（无 CI，见 O5-05），所以这类缺失不会被任何自动化发现。
- **命中形态**：任何启用了 HTTPS 的部署（推荐形态）命中；纯 HTTP 部署不受影响。
- **验证命令**：
  ```bash
  git grep -n "SECURE_" master -- backend/backend/settings.py      # 无输出
  git show master:backend/logviewer/logviewer/settings.py | sed -n '53p;59,64p'
  git show master:deploy/nginx-gipfel.conf | sed -n '53p'
  ```
- **既有审计重叠**：无（既有 U04「backend-production」篇未覆盖 `SECURE_PROXY_SSL_HEADER` 缺失）。
- **建议方向**：补 `SECURE_PROXY_SSL_HEADER`；按是否 HTTPS 显式开关 `SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE`（与日志查看器同构，可从同一 `.env` 变量派生）；HSTS 交由 nginx 与 Django 二选一，避免重复；把 `manage.py check --deploy` 纳入发布门禁。

## 证据方法说明（供总报告引用）

- 用 `git archive master` 在 Windows 上导出会因 `core.autocrlf` 把文本文件转成 CRLF，与 master blob 不一致：同一文件 `deploy-linux.sh` 在旧导出中有 652 个 CR 字节，而 `git cat-file blob` 实测为 0。本报告全部行号与引用均改由 `git -c core.autocrlf=false -c core.eol=lf archive` 导出的逐字节快照得出，并用 read/grep/git-show 三方交叉核对了每条 `file:line`。
- 所有"验证命令"均为只读命令，可在仓库根目录直接执行（`git show master:<path>` 读的是对象库，不受当前 checkout 在 `bugfix-merged` 分支影响）。
