### [P1] O1-01 重跑 `deploy-linux.sh` 用 `enable --now` 而非 `restart`：已运行的服务**不会**被重启，新代码/新库结构/新前端全部落盘但线上进程仍是旧代码，脚本却打印「gipfel.service 运行中 / 部署完成」

- 证据：`scripts/deploy-linux.sh:472`（master@97e117e）—— `systemctl enable --now gipfel 2>/dev/null || warn "systemctl enable --now gipfel 失败（unit 可能仍被 masked），详见下方活性检查"`；`:483` 同款 `systemctl enable --now gipfel-logviewer`；`:15` 步骤注释亦为 `6. systemd unit gipfel.service enable --now`。对照升级脚本：`scripts/update-from-github.sh:441` `systemctl restart gipfel`、`:457` `systemctl restart gipfel-logviewer`。文档承诺见 `deploy/README.md:230`：「`deploy-linux.sh` 同样会备份/恢复数据并 restart；……**两种路径效果一致**」。
- 现状：`deploy-linux.sh` 全文没有 `systemctl stop`/`systemctl restart`（`grep` 确认：仅 `unmask`/`daemon-reload`/`enable --now`/`is-active`/`reload nginx`/`start nginx`）。`enable --now` 的 `start` 对**已 active** 的 unit 是 no-op；脚本第 474-480 行的验收只有 `systemctl is-active --quiet gipfel`，旧进程同样满足该条件。因此重跑部署时：代码被 rsync 覆盖（184-190）、`migrate` 已执行（410）、`frontend-dist` 已换新（429-431）、`.venv` 依赖已更新（404）——**只有正在运行的 Python 进程还是旧的**，直到手工 restart、进程崩溃被 `Restart=always`（`deploy/gipfel.service:32`）拉起或整机重启才切换。
- 运维影响：一次「部署成功」的假象会把故障推迟到不可预期的时间点爆发——库结构已被新迁移改写，而旧代码还在用旧字段名读写；若迁移含字段改名/删除或 RunPython 数据变换，旧进程会在写入时报错（500）或写回旧格式数据（新旧格式混杂，迁移脚本再跑也修不回）。若只改了 `deploy/*.service`（例如 8121 端口修复），新 unit 已落 `/etc/systemd/system` 且 `daemon-reload` 过，但线上仍按旧 unit 跑，运维会得出「修了没用」的错误结论。恢复方式是手工 `systemctl restart gipfel gipfel-logviewer`，但在「部署完成」的绿灯下没人会想起来。
- 命中形态：默认部署命令 `sudo bash scripts/deploy-linux.sh --install-dir /opt/gipfel --with-nginx` **命中**。首次部署：不命中（服务本就不存在，`enable --now` 即首次启动，正确）；重跑：**命中**（最常见用途，尤其是 README:225-230 推荐的「等价做法」）；升级：**命中**（`update-from-github.sh` 的 restart 不命中，但 README 明确宣称两者等价，实际行为相反）。
- 验证命令：`git show master:scripts/deploy-linux.sh | Select-String -Pattern 'systemctl (stop|restart)|enable --now'`（预期：只有两处 `enable --now`，无 stop/restart）；`git show master:deploy/README.md | Select-Object -Skip 229 -First 1`
- 既有审计重叠：无（U14 X-10 只讲「无回滚、无 trap」，X-24 讲 nginx 退出码，X-07 讲升级脚本 pull 失败，均未涉及「重跑 deploy-linux.sh 不重启服务导致发布不生效」；本条为其独立发现，且新信息是 README:230「两种路径效果一致」这一文档承诺与实现相反）。
- 建议方向：把 `enable --now` 改为 `systemctl enable` + 明确的 `systemctl restart`（或 stop→操作→start 的窗口化流程），并在收尾验收中断言「进程启动时间 / 加载的 commit」晚于本次部署开始时间，把结论并入退出码。

### [P1] O1-02 `update-from-github.sh` 在 systemd 单元刷新失败时**跳过全部重启**，随后仍以 `exit 0` 收尾：CI/自动化判定升级成功，实际线上仍是旧代码 + 新库结构

- 证据：`scripts/update-from-github.sh:436-438`—— `if [[ "$UNIT_REFRESH_FAILED" == 1 ]]; then warn "服务单元未能正常启用（masked 等问题未解除），本次跳过全部重启，避免用旧状态误判。"`；`:452-454` 日志查看器同理；`:599-600`—— `# 明确退出，避免依赖上一条命令的偶然退出码` / `exit 0`。
- 现状：`refresh_unit` 两次尝试仍失败（unit 仍 masked / 模板为空且无法恢复 / `systemctl enable` 失败）时置 `UNIT_REFRESH_FAILED=1`（432-433），脚本刻意跳过 `restart gipfel`/`restart gipfel-logviewer`（439-450、455-466），但**继续执行** nginx 段（469-571），最后无条件 `exit 0`。此时磁盘上已是新代码、库已 `migrate`（235）、静态资源已重建（236-240）、前端已重建（253-256），只有进程没重启。脚本只留下两行 `[WARN]`，进程退出码 0。
- 运维影响：这是「服务已然是旧状态、但自动化认为已发布」的典型形态：`&&` 串联的发布流水线、CI job、cron 升级任务都无法据此判定失败；错过的修复（例如日志查看器 8121 端口修复、ExecStart 变更）继续不生效，而监控只看到服务一直 active。恢复需要人工读 WARN 并手工 `daemon-reload && restart`，排障时最容易被忽略的正是这类「成功输出里的两行黄字」。
- 命中形态：默认升级命令（`update-from-github.sh --source-dir ... --install-dir /opt/gipfel --with-nginx`）在 unit 刷新失败这个前提成立时命中；首次部署不命中（首次部署走 `deploy-linux.sh`，其失败路径用 `err` 退出 1）；重跑/升级路径命中（触发前提是历史上真实发生过的 masked/空模板问题，脚本注释自述为「真实事故」）。
- 验证命令：`git show master:scripts/update-from-github.sh | Select-Object -Skip 435 -First 4` 与 `... | Select-Object -Skip 598 -First 2`
- 既有审计重叠：与 U14 X-24 同源（同属「失败仍退出 0」）。**新信息**：① X-24 指向的 `deploy-linux.sh:559-568` 在 master 上其实**不成立**——`systemctl reload nginx`/`start nginx` 处于 `if` 分支体内，`set -e` 下失败即非 0 退出，`nginx -t` 失败走 `err`（退出 1）；真正「失败却退出 0」的位置是 574-580 的**校验性 warn**（80 端口仍返回欢迎页等）；② 本条是另一处代码位置（436-438 + 599-600 的显式 `exit 0`），后果是「跳过重启 + 退出 0」的组合，比 X-24 的 nginx 场景更严重（升级整体未生效）。
- 建议方向：`UNIT_REFRESH_FAILED` 等降级标志应在收尾汇总为「非 0 退出码 + 失败清单」；即使保留 `warn` 继续，也应至少把「未重启」写进退出码与最终摘要，避免 CI 误判。

### [P1] O1-03 备份是**服务运行中的活库 `cp`**（无停服、无 `-wal`/`-journal`、无 SQLite 备份接口、无完整性校验），而它是脚本与文档给出的唯一回滚依据

- 证据：`scripts/deploy-linux.sh:175`—— `cp -a "$INSTALL_DIR/backend/db.sqlite3" "$BACKUP_DIR/" 2>/dev/null || true`；`scripts/update-from-github.sh:192`—— `cp -a "$INSTALL_DIR/backend/db.sqlite3" "$BACKUP_DIR/" && log "已备份数据库 → $BACKUP_DIR/db.sqlite3"`；回滚依据见 `deploy/README.md:234-238`；服务是 `Restart=always` 的常驻进程（`deploy/gipfel.service:32`），两个脚本全文无 `systemctl stop`（`grep` 确认）。
- 现状：备份发生在升级/重部署的**最前面**（deploy 172-178；update 188-195），此时线上 daphne 仍在处理请求与写 SQLite。复制只取主库文件：不取 `db.sqlite3-wal` / `db.sqlite3-shm`（若日后启用 WAL），不取 `db.sqlite3-journal`（默认 rollback journal 模式下热日志存在时），也不做 `PRAGMA integrity_check` 或行数比对。`settings.py` 的 SQLite 配置无 `OPTIONS`/`journal_mode`（默认 DELETE 日志模式），因此「复制到半写页 + 丢失日志文件」是可达的一致性问题，而脚本没有任何一致性保证。
- 运维影响：备份恰恰在「需要恢复」时才被用到——Django 的 SQLite 写入本身是事务性的，但**文件级 cp 不是**：崩在恢复时刻会得到 `database disk image is malformed`，或静默丢掉最近若干已提交事务（用户/订单/比赛数据）。因为脚本与文档都把 `_backup/<ts>` 描述为「回滚即可」（`update-from-github.sh:447/463` 的 `err` 提示、`deploy/README.md:235` 的注释「最近的完整复制回来」），运维在有备份的心理预期下可能放弃更重的补救手段（如从旧机/从库恢复），把小故障放大成真实数据丢失。
- 命中形态：默认部署/升级命令均命中（只要已有实例就进入备份分支）；首次部署不命中（无库可备）；重跑命中；升级命中。
- 验证命令：`git show master:scripts/deploy-linux.sh | Select-Object -Skip 174 -First 1`；`git show master:scripts/deploy-linux.sh | Select-String -Pattern 'systemctl stop|wal|VACUUM|\.backup|integrity_check'`（预期无输出）
- 既有审计重叠：与 U14 X-05 同源（同一机制：对活库做文件级拷贝）+ X-10 相邻（备份不含代码）。**新信息**：X-05 针对的是 `quick-sync.sh` 的跨机 `rsync db.sqlite3`；本条是**两个部署脚本自身的备份**（deploy:175 / update:192），成因不同（就地 `cp` 同机、且**从不先停服**，连 `--exclude` 保护都在），后果不同（真回滚时备份不可用）；X-10 指出了「备份无法回滚代码」，但把该备份当作可信数据源，未评估其一致性。
- 建议方向：备份前后用 SQLite 官方接口取一致性快照（`sqlite3 db.sqlite3 ".backup"` / `VACUUM INTO`，或 Django `manage.py dumpdata`），并做 `PRAGMA integrity_check` + 关键表行数记录；或明确在停服窗口内备份，并把「本次备份是否一致」纳入部署摘要。

### [P1] O1-04 `chown -R gipfel:gipfel "$INSTALL_DIR"` 把 `.venv`、`manage.py`、`deploy/*.service`、`scripts/`、`_backup/` 整体交给运行账户：**下一次以 root 运行的部署会执行这些文件**，应用层任意写文件即可提权为 root，且应用可删改自己的全部备份

- 证据：`scripts/deploy-linux.sh:437`—— `chown -R gipfel:gipfel "$INSTALL_DIR"`；`scripts/update-from-github.sh:261` 同款；root 随后执行安装树内的文件：`deploy-linux.sh:404` `".venv/bin/pip" install -r requirements.txt`、`:410` `".venv/bin/python" manage.py migrate --noinput`、`update-from-github.sh:233-236` 同款；备份目录也在安装树内：`deploy-linux.sh:80` `BACKUP_DIR="${INSTALL_DIR}/_backup/$(date +%F_%H%M%S)"`。

### [P1] O1-05 首次部署时 `.env`（含 JWT_SECRET / DJANGO_SECRET_KEY / LOGVIEWER_SECRET_KEY / SEED_ADMIN_PASSWORD）从 `.env.example` 复制后是 **0644**，直到第 438 行才 `chmod 600`；中间任何一步失败都会让全部密钥永久停在同机可读状态

- 证据：`scripts/deploy-linux.sh:210`—— `cp "$INSTALL_DIR/backend/.env.example" "$INSTALL_DIR/backend/.env"`（`git ls-tree master backend/.env.example` → `100644`，`cp` 不带 `-p`，默认 umask 022 下产物即 `644`）；随后写入全部密钥：`:214-216` JWT_SECRET、`:219-226` DJANGO_SECRET_KEY、`:277-291` LOGVIEWER_SECRET_KEY、`SEED_ADMIN_PASSWORD`；`:438` 才是—— `chmod 600 "$INSTALL_DIR/backend/.env" 2>/dev/null || true`（中间隔着 pip install 404、migrate 410、collectstatic 411-415、npm ci/build 421-431）。
- 现状：密钥落盘的时刻（210-291）与权限收紧的时刻（438）之间是完整依赖安装 + 迁移 + 前端构建，耗时从数分钟到数十分钟（首次 `npm ci` 尤其长）。第 438 行的 `|| true` 还意味着即使 chmod 本身失败也不会告警。已存在的部署不受影响（下次备份携带 600 权限，重跑时 `.env` 仍是 600）。
- 运维影响：两个场景——① 窗口期内同机任意本地用户（其他服务账户、被入侵的低权进程、共享跳板机上的其他租户）可直接 `cat` 出 JWT_SECRET，据此伪造任意用户（含 SUPER_ADMIN）的 JWT，以及 DJANGO_SECRET_KEY（伪造 session/CSRF）、LOGVIEWER_SECRET_KEY（自签日志查看器与 `/admin` 防直连令牌）；② 更常见的是部署在窗口内失败（`npm run build` 失败、pip 拉包超时、磁盘满），脚本 `set -e` 退出，`.env` **永久**停在 0644，而运维只看到构建报错、不会想到密钥权限——除非重跑一次完整成功的部署。安全边界（网关令牌、Host 白名单）在密钥泄露后全部失效且无任何日志痕迹。
- 命中形态：默认部署命令命中；首次部署命中（唯一会新生成密钥的路径）；重跑不命中（`.env` 已存在且已 600，除非上次失败留下 644）；升级不命中。
- 验证命令：`git show master:scripts/deploy-linux.sh | Select-Object -Skip 209 -First 2` 与 `... | Select-Object -Skip 437 -First 1`；`git ls-tree master backend/.env.example`

- 建议方向：创建 `.env` 时立刻 `install -m 600`（或在 `umask 077` 子 shell 内生成），后续所有 `sed -i` 之后立即复核 `stat -c %a`，并把「.env 权限 = 600」作为收尾断言/退出码的一部分。

### [P2] O1-06 前端发布不是原子替换：先 `rm -rf frontend-dist` 再 `cp`，而 nginx 的 `try_files` 兜底会把「缺文件」变成 text/html 白屏、把「空目录」变成 500；失败/中断会留下长期损坏的发布产物
