### [P1] O4-01 文档给出的唯一"定期备份"方案是活库裸 `cp`（不停服、无一致性手段），且 db 与 uploads 分两次复制存在时间窗——每日备份的 RPO 实际上不可信

- 证据：`docs/MIGRATION.md:506`（master@97e117e）—— `cp -a /opt/gipfel/backend/db.sqlite3 "$BACKUP_DIR/"`；`:508` —— `cp -a /opt/gipfel/backend/uploads "$BACKUP_DIR/"`；`:504-505` —— `BACKUP_DIR="/opt/gipfel/_backup/$(date +%Y%m%d_%H%M%S)"` / `mkdir -p "$BACKUP_DIR"`；该脚本由 `:515` —— `echo "0 3 * * * /opt/gipfel/scripts/backup.sh" | sudo crontab -` 每天 3 点触发。对照：全仓无 `journal_mode`/`PRAGMA`/`busy_timeout`（`git grep ... master -- "*.py" "*.sh" "*.md" "*.conf"` 无输出），`backend/backend/settings.py:304-309` 的 `DATABASES` 无 `OPTIONS`。
- 现状：`MIGRATION.md` §7.3 是仓库里唯一给出"频率 + 落地方式"的自动备份方案。它由 root crontab 触发，备份期间 `gipfel.service`/`gipfel-logviewer.service`（`Restart=always` 的常驻 daphne）继续读写同一个 `db.sqlite3`；脚本先 `cp` 主库、再 `cp` uploads（两次独立复制），全程不停止服务、不加锁、不调用 SQLite 备份接口，也不记录任何一致性判据。文档内部并不自洽：§4.1 的手动迁移路径**先停服再 `cp`**（`docs/MIGRATION.md:180-181`），而 §7.3 与两个部署脚本（`scripts/deploy-linux.sh:175`、`scripts/update-from-github.sh:192`）都不停服。
- 运维影响：默认 rollback journal 模式下热拷主库可能得到（a）**含未提交修改的页**——`cp` 落在写事务中途，这些修改在源库会被日志回滚、却永久留在备份里；（b）**新旧内容混杂的撕裂页**——`cp` 边读边被写，恢复后 `PRAGMA integrity_check` 可能直接报 `malformed`。两种形态在 `cp` 成功、文件大小正常、`echo 备份完成` 正常打印的情况下都看不出来。等到真需要恢复（业务误删、库损坏、磁盘故障）时，"每天 3 点有备份"的心理预期会让运维放弃更重的补救手段，把可恢复故障放大成真实数据丢失。uploads 与 db 分两次复制还带来跨目录时间窗：先拍 db 快照、后拷 uploads，窗口内新提交的"文件+记录"只在 uploads 里（无害的孤儿文件）；反之若窗口内发生删除，则备份里会出现指向已删文件的悬空记录——两侧都不做校验，运维无法判断手上这份备份处于哪种状态。
- 命中形态：**首次部署**不命中（无库可备，crontab 只有在运维照 §7.3 手工执行后才存在）；**日常升级**不命中本节（走 O1-03 的部署时备份），但若已按 §7.3 建了 cron 则每天命中一次；**服务器迁移**：`migrate-server.sh` push 模式直接 `rsync` 活库、pull 模式 `rsync` 远端活库（`scripts/migrate-server.sh:215-225`、`323-335`，`DATA_ITEMS` 含 `backend/db.sqlite3`），同样命中热拷贝。
- 验证命令：`git show master:docs/MIGRATION.md | sed -n '496,516p'; echo "--- 是否有停服/一致性手段 ---"; git grep -n -i -E "journal_mode|PRAGMA|VACUUM INTO|systemctl stop" master -- docs/MIGRATION.md scripts/quick-sync.sh scripts/migrate-server.sh`（预期：备份段落无 stop、无 PRAGMA）
- 既有审计重叠：**与 U14 X-05 同源**（同一根因：对活库做文件级拷贝）+ **与 O1-03 同源**（O1-03 覆盖的是两个部署脚本自身的 `_backup`，`deploy-linux.sh:175` / `update-from-github.sh:192`）。**我的新信息**：① 本条覆盖的是**文档推荐的定时备份**（`docs/MIGRATION.md:500-515`），它是仓库里唯一面向"日常 RPO"的机制，O1-03 与 U14 X-05 都未涉及；② 更正 X-05 的 WAL 表述：master 未启用 WAL，缺失的是 `db.sqlite3-journal` 与一致性保证，不是 `-wal`/`-shm`；③ 指出文档自相矛盾（§4.1 停服备份 vs §7.3/脚本不停服）。
- 建议方向：备份统一走 SQLite 官方一致性接口（`sqlite3 db ".backup"` / `VACUUM INTO`，或停服窗口内 `cp`），并在同一快照事务内处理 uploads（或至少固定"先库后文件"的顺序并记录时间戳）；备份完成后立刻 `PRAGMA integrity_check` + 关键表行数留档，把结果写入备份目录内的 manifest，供恢复前核对。
