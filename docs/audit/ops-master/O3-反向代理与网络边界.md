### [P2] O3-05 `upstream ... keepalive 32` 完全不生效：没有任何 location 清空 `Connection`，nginx 默认向上游发 `Connection: close`；`/socket.io/` 又把 `upgrade` 写死

- 证据：`deploy/nginx-gipfel.conf:12`（master@97e117e）—— `    keepalive 32;`；`deploy/nginx-gipfel.conf:49-50` —— `        proxy_http_version 1.1;` / `        proxy_set_header Host              $host;`（同一「`proxy_http_version 1.1` + `Host $host`、无 `Connection`」模式还出现在 `:64`/`:67`、`:111`/`:112`、`:140`/`:141`、`:219`、`:275`、`:330`/`:331`、`:340`/`:343`、`:372`/`:373`）
- 现状：nginx 的 `proxy_set_header` 默认只重定义两个头——`Host: $proxy_host` 和 `Connection: close`；要启用 upstream keepalive 必须显式 `proxy_set_header Connection "";`。模板里 8 处代理 location 无一清空 `Connection`，唯一显式设置它的是 `/socket.io/`（`:66` `proxy_set_header Connection        "upgrade";`，写死字面量，不是 `$connection_upgrade` map）。此外 `location = /api/health`（`:108-114`）只传了 `Host` 与 `X-Real-IP`，连 `X-Forwarded-For`/`X-Forwarded-Proto` 都没有，与真实 API 链路的头集合不一致。
- 运维影响：`keepalive 32` 形同虚设——每个 `/api/`、`/admin/` 请求都新建一条到 127.0.0.1:8000 的 TCP 连接并立即关闭，单进程 daphne 承受持续 accept/close churn，压测或前端并发轮询（前端每页多条 API + 心跳）下会积累大量 TIME_WAIT 并放大延迟；`/socket.io/` 的轮询（polling）请求也因写死 `Connection: upgrade` 而无法回池复用（`Upgrade: $http_upgrade` 在无升级头时为空值被 nginx 丢弃，但 `Connection: upgrade` 字面量仍发出）。维护者读注释会以为已做了连接复用优化，实际没有。
- 命中形态：两种形态都命中（与域名/IP 无关，属代理实现层）。
- 验证命令：`grep -n "keepalive\|Connection\|proxy_http_version\|location = /api/health" "$SNAP/deploy/nginx-gipfel.conf"`
- 既有审计重叠：无。
- 建议方向：每个代理 location 补 `proxy_set_header Connection "";`（WebSocket 用标准 `map $http_upgrade $connection_upgrade` 写法，避免把 `upgrade` 写死到轮询请求上）；健康检查 location 补齐 `X-Forwarded-For`/`X-Forwarded-Proto`，使探活链路与被代理链路一致；补一条「复用生效」的自检说明（如 `ss -tn state established '( dport = :8000 )'` 观察连接数）。
