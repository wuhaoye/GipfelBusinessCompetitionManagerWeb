## 缺陷清单

### [P1] O2-01 `ProtectSystem=full` 根本不保护 `/opt`：unit 自述的"文件系统只读 + 仅开放必要可写路径"是假的，服务账号对源码/`.venv`/`.env`/`frontend-dist` 全部可写

- 证据：`deploy/gipfel.service:37`、`:40`、`:52`（master@97e117e）—— 原文行
  - `:37  # 沙箱加固（M9）：最小权限 + 文件系统只读 + 仅开放必要可写路径`
  - `:40  ProtectSystem=full`
  - `:52  ReadWritePaths=__INSTALL_DIR__/backend/uploads __INSTALL_DIR__/backend/logs __INSTALL_DIR__/backend/db.sqlite3 /run/gipfel /var/log/gipfel`
  - 同款三行见 `deploy/logviewer.service:39`、`:42`、`:53`
- 现状：`ProtectSystem=full` 只把 `/usr`、`/boot`、`/efi`、`/etc` 挂为只读（上游 systemd.exec(5) 明确列出路径），`strict` 才是"整个文件系统只读"。默认安装目录 `deploy/README.md:89` 为 `/opt/gipfel`，位于 `/opt` 下，因此该 unit 的文件系统视图里 `/opt/gipfel/backend/backend/*.py`、`backend/.venv/`、`backend/.env`、`/opt/gipfel/frontend-dist/` **全部保持可写**。`ReadWritePaths=` 只在文件系统已被挂只读时才有"放开"意义，此处既不放宽也不限制，是一份无约束力的清单；脚本 `scripts/deploy-linux.sh:437` 把整棵安装树 `chown -R gipfel:gipfel`，两个服务又都是 `User=gipfel`（`gipfel.service:9`、`logviewer.service:9`），即同一 UID 对这些文件均有写权限。
- 运维影响：任何以 gipfel 身份执行的代码（日志查看器本身就是"读日志 + 渲染日志内容"的低信任站点、上传解析路径、依赖链投毒）都能**立即**改写 `/opt/gipfel/frontend-dist/`（nginx 直接以静态文件托管该目录：`deploy/nginx-gipfel.conf:37  root __INSTALL_DIR__/frontend-dist;`，`deploy/README.md:97`）→ 对全体浏览器注入脚本，无需重启；或改写 `.env` 的 `JWT_SECRET`/`LOGVIEWER_SECRET_KEY`（`backend/backend/settings.py:23`、`:47`）→ 等下一次重启即可伪造任意用户 JWT / 伪造网关令牌；改写 `backend/backend/asgi.py` 则下次重启即持久化 RCE。也就是说，日志查看器被拿下 = 主服务被拿下，而 unit 的注释会让运维相信"源码只读、只有 uploads/logs/db 可写"。
- 命中形态：默认部署形态即命中——注释承诺与实际内核挂载结果相反，无需任何特殊条件。
  - 首次部署：`ProtectSystem=full` 生效后 `/opt/gipfel` 依旧可写。
  - 服务重启：无变化，仍可写。
  - 运行期：攻击/事故链成立：改 `frontend-dist`（立即）、改源码/`.env`（下次重启）。
- 验证命令（只读，快照内）：
  `Select-String -Path "$env:snap\deploy\gipfel.service","$env:snap\deploy\logviewer.service" -Pattern 'ProtectSystem|ReadWritePaths|chown'`（`$env:snap` = 快照目录）
  部署机只读复核：`systemctl show gipfel -p ProtectSystem -p ReadWritePaths -p User`，再对照 `man systemd.exec` 的 `ProtectSystem=` 段（`full` 不含 `/opt`）。
- 既有审计重叠：与 U14 X-13 同源（都涉及 `ReadWritePaths` 与主应用可写路径）——**新信息**：X-13 的前提是"ReadWritePaths 授予了主应用可写路径"，而在 `ProtectSystem=full` 下该指令**毫无约束力**，越权面也不止列出的三个路径，而是整棵 `/opt/gipfel`（含源码、`.venv`、`.env`、`frontend-dist`），且两个服务同 UID，无任何隔离；`/var/log/gipfel` 条目同样是冗余的（`/var` 本就不在 `full` 的只读集合内）。
- 建议方向：把 `ProtectSystem=strict` 与 `ReadWritePaths=`（补上真正需要的路径）配套使用；把源码/`.venv`/`frontend-dist` 放在服务账号只读的路径或单独只读挂载上；两个服务拆成不同 UID；至少让注释与实际语义一致。

### [P1] O2-02 `Restart=always` + `RestartSec=3s` 永远达不到默认 `StartLimitBurst=5`，服务进入"永久 3s 重启循环但永不 failed"：没有 failed 状态可告警，`.env` 缺失/端口被占等致命错误表现为无限 502

- 证据：`deploy/gipfel.service:32-33`、`:15`、`deploy/logviewer.service:34-35`、`:16`（master@97e117e）—— 原文行
  - `gipfel.service:32  Restart=always` / `:33  RestartSec=3s`
  - `gipfel.service:15  EnvironmentFile=-__INSTALL_DIR__/backend/.env`（`-` = 文件缺失不报错）
  - `logviewer.service:16  EnvironmentFile=-__INSTALL_DIR__/backend/.env`
  - 无 `StartLimitIntervalSec=` / `StartLimitBurst=` / `OnFailure=`
  - 失败源：`backend/backend/settings.py:24-26`（`JWT_SECRET` 为空直接 `raise RuntimeError`）、`backend/logviewer/logviewer/settings.py:29-35`（`LOGVIEWER_SECRET_KEY` 为空 `raise RuntimeError`）
- 现状：默认 `StartLimitBurst=5` / `StartLimitIntervalSec=10s`，而 `RestartSec=3s` 决定两次启动尝试的最小间隔 ≥3s，任何 10s 滑动窗口内最多 4 次启动尝试（0/3/6/9s），**永远到不了第 5 次**，限流不可能触发。后果是：单元不会进入 `failed`，永久停留在 `activating (auto-restart)`，`systemctl is-failed` 恒为假，任何"基于 failed 单元"的监控/告警（含 `OnFailure=`）都不会响；同时 journald 每 3s 收到一条启动失败记录（约 2.9 万条/天，仅有 journald 自身的容量上限兜底）。触发这一循环的常见原因在仓库里是现成的：`.env` 被误删/改名（两个服务都是可选读取 + settings fail-fast），或 8000 端口已被占用——后者尤其现实，因为 `docs/OPS.md:77` 仍把 `python manage.py rundaphne` 写作"生产启动"命令，运维照做后 systemd 里的 daphne 会因 `listen_error → stop()`（`daphne/server.py:166-168`）立即退出并进入无限重启。相反方向的语义也一并缺失：`Restart=always` 对"进程活着但每个请求都 500"完全不动作（见 O2-08）。
- 运维影响：何时爆——任何一次致命配置错误或端口冲突；爆了会怎样——外网持续 502/nginx 502，`systemctl status` 显示 active-ish 的 auto-restart 而非 failed，运维无法靠 `is-failed`/告警发现，只能靠人工看 journal；journal 被每 3s 一条的堆栈持续写入。
- 命中形态：默认部署形态不命中（正常部署能起来）；一旦出现致命配置错误/端口冲突即命中，且是"永久"而非"限流后停下"。
  - 首次部署：`.env` 由脚本生成，一般不触发。
  - 服务重启：若 `.env` 缺失或端口被占，进入无限循环。
  - 运行期：无 failed 状态可观测，只有 journal 有痕迹。
- 验证命令（只读）：`systemctl show gipfel -p Restart -p RestartUSec -p StartLimitBurst -p StartLimitIntervalUSec -p DefaultStartLimitBurst -p DefaultStartLimitIntervalUSec -p OnFailure`（若返回 10s/5，即证明 3s 间隔无法在一次窗口内凑满 5 次），并把 `RestartUSec` 与 `DefaultStartLimitIntervalUSec` 相除即可自证。
- 既有审计重叠：无（X-01…X-29 未涉及 `StartLimit*`/`OnFailure` 与 `RestartSec` 的组合）。
- 建议方向：显式配置 `StartLimitIntervalSec=`/`StartLimitBurst=` 使崩溃循环能落到 `failed`；加 `OnFailure=` 或外部探活告警；`EnvironmentFile=` 保持可选的同时补一条启动前校验（如 `ExecStartPre=` 检查 `.env` 关键键），让"配置缺失"变成一次性可见失败而不是无限重启。

### [P1] O2-03 两个 daphne access log 完全没有轮转（仓库内零 logrotate 配置），且 daphne 长期持有文件句柄使常规 rename 轮转无效 → 磁盘写满后 SQLite 写入失败、全站 500

- 证据：`deploy/gipfel.service:22`、`deploy/logviewer.service:24`、`backend/backend/settings.py:432-440`（master@97e117e）—— 原文行
  - `gipfel.service:22      --access-log /var/log/gipfel/access.log \`
  - `logviewer.service:24      --access-log /var/log/gipfel/logviewer.access.log \`
  - `settings.py:433  "class": "logging.handlers.TimedRotatingFileHandler",` / `:435  "when": "midnight",` / `:436  "backupCount": 14,`（**无 `maxBytes`**）
  - `docs/OPS.md:91`：`- **后端运行日志**：backend/logs/gipfel.log（按天滚动，保留 14 天）；生产亦可用 journalctl -u gipfel -f。`
- 现状：仓库内不存在任何 logrotate 配置（`grep -rn logrotate` 对整棵 master 快照 0 命中），`LogsDirectory=gipfel`（`gipfel.service:29-30`）只负责建目录与属主，不做轮转、不做容量上限。daphne 的 access log 在进程启动时 `open(args.access_log, "a", 1)` 打开一次（`daphne/cli.py:227`，见 `daphne==4.1.2` 源码），此后一直往同一 fd 写（`daphne/access.py:59-69`），文件永不切换、永不清空；每条 HTTP 请求写 1 行、每次 WS 连接/断开各写 1 行（`daphne/access.py:18-50`），且请求行含完整 URI（`daphne/http_protocol.py:277-297`）。唯一"被轮转"的只有 Django 的 `gipfel.log`，而它的 `TimedRotatingFileHandler` 没有 `maxBytes`，单日文件可以无限大，只按"文件个数"保留 14 份。
- 运维影响：何时爆——随请求量线性增长，单机跑满一个学期/一场比赛后 `access.log` 到 GB 级；爆了会怎样——磁盘写满后 SQLite 报 `database or disk is full`（业务写全 500，且此时 `gipfel.log` 自己也写不进去），`deploy/update` 脚本的备份/`migrate` 也会失败。另一个隐性坑：因为 daphne 只持有 fd，**事后补一个 logrotate 用默认的 rename+create 方式也不生效**（日志会继续写进被改名的旧文件，直到重启），只有 `copytruncate` 或重启才有效。
- 命中形态：默认部署形态即命中（两个 unit 原样落地就带 `--access-log`，而仓库不提供任何轮转）。
  - 首次部署：无轮转即开始累积。
  - 服务重启：access log 继续追加（`"a"` 模式），不会截断；重启是唯一"换新文件"的机会（也没人做）。
  - 运行期：长时间运行线性增长，最终磁盘满。
- 验证命令（只读）：`grep -rn "logrotate" <快照>`（0 命中）+ `grep -n "access-log" <快照>/deploy/*.service` + `grep -n "backupCount\|maxBytes" <快照>/backend/backend/settings.py`；部署机只读复核：`ls -l /var/log/gipfel/ && du -sh /var/log/gipfel/*`（可直接看到无 `.1`/`.gz` 轮转产物与当前体积）。
- 既有审计重叠：无（X-01…X-29 未覆盖 access log 轮转；X-13 只提到 `LogsDirectoryMode=0755` 的目录可读性）。
- 建议方向：为 `/var/log/gipfel/*.log` 提供 `copytruncate` 的 logrotate 配置并纳入部署脚本；给 `TimedRotatingFileHandler` 加 `maxBytes` 形成"按天 + 按大小"双条件；对 `/var` 用量加一条外部监控。

### [P1] O2-04 财年定时器在 HTTP 请求内同步跑完，且并发触发被静默跳过、重启/超时中断后无法续跑：财年已置 CLOSED 而部分公司字段仍为旧值，接口却全部返回成功

- 证据：`backend/apps/company_fields/timer.py:154-167`、`:199-203`、`:239-242`，`backend/apps/competitions/views.py:227-236`（master@97e117e）—— 原文行
  - `timer.py:159  if not lock.acquire(blocking=False):` / `:160-163  logger.warning("财年定时器：比赛 #%s 的 %s 已在执行中，跳过本次并发触发", …)` / `:163  return`（**返回 None，调用方不区分**）
  - `views.py:227  fy.save()` → `:233-236  if prev_status != "ACTIVE" and new_status == "ACTIVE": _apply_fiscal_year_timer(...) / elif prev_status != "CLOSED" and new_status == "CLOSED": _apply_fiscal_year_timer(...)`，随后 `:237  return Response(FiscalYearSerializer(fy).data)`
  - `views.py:45-55  def _apply_fiscal_year_timer(...): _impl(competition_id, trigger)`（返回值被丢弃）
  - `timer.py:239-242  if pending: with transaction.atomic(): for industry_field_id, value in pending: _write_field_value(...)`（**逐公司一个小事务**，无全局事务、无进度标记）
- 现状：`POST/PATCH` 财年接口在 `fy.save()` **提交之后**才同步调用定时器，请求线程内逐公司、逐字段写入并做级联重算，全部完成后才返回 200。同一比赛的第二次触发因进程内非阻塞锁直接 `return`（只写一条 warning），调用方拿不到任何"被跳过"的信号，响应与真跑完完全一样。中断路径也是敞开的：nginx 对 `/api/` 的 `proxy_read_timeout` 是 120s（`deploy/nginx-gipfel.conf:47-55`），公司数×字段数×重算耗时超 120s 时客户端拿到 504 而后端仍在写；`systemctl restart gipfel` 时 daphne 收到 SIGTERM 会 `kill_all_applications()` 立刻 cancel 所有在途应用协程（`daphne/server.py:144`、`:150`、`:170-177`），请求被丢弃。而恢复路径几乎不存在：定时器只由"状态跃迁"驱动（`views.py:233-236`），财年已是 CLOSED 时再关闭不会重跑，仓库也没有任何手动触发定时器的接口（`backend/apps/company_fields/urls.py` 只有字段读写两条路由）；唯一的土办法是把状态改回 ACTIVE 再改回 CLOSED，而那会先跑一遍 FY_START，把已写好的值再覆盖一次。
- 运维影响：何时爆——一场比赛公司数量上去后（数百家公司 × 若干定时器字段 + 每个公司一次级联重算）任何一次财年切换、或切换过程中恰好重启/网络超时；爆了会怎样——财年在界面上显示已关闭，但只有部分公司换了新值，前端拿到的是"成功"，没有任何地方记录进度或失败公司清单，之后很难判定哪些公司漏算，只能人工比对或全量重跑（全量重跑又有覆盖副作用）。
- 命中形态：默认部署形态即命中机制（单进程 + 进程内锁 + 请求内同步执行 + 无进度标记），数据量小的时候不会暴露。
  - 首次部署：无影响（没数据）。

### [P2] O2-09 `TimeoutStopSec=30` 与 daphne 的实际关停语义不匹配：收到 SIGTERM 即 cancel 所有在途请求、长连接无关闭帧，30s 的"优雅退出窗口"从未被使用

- 验证命令（只读）：`grep -n "KillSignal\|TimeoutStopSec\|KillMode" <快照>/deploy/*.service`；源码复核（只读）：`grep -n "kill_all_applications\|reactor.run\|def stop" <venv>/daphne/server.py`。
- 既有审计重叠：无。
- 建议方向：接受"重启即硬断"这一事实并在客户端保证重连/幂等（前端已有 sync:replay 机制，但需确认断连期间的写操作有幂等键）；或改用支持优雅退出的进程管理方式（`--graceful-timeout` 类参数/`KillMode=mixed` + 应用层 drain），并让 `TimeoutStopSec` 与真实排空时间对齐。

### [P3] O2-12 环境变量契约与文档声明不一致：`PATH` 被覆盖成单一 venv 目录（无 `/usr/bin`），而 `.env` 的 `PORT` 被称为"单一真源"，在 systemd 形态下实际被 `-p 8000` 硬编码覆盖

  - 首次部署：`PORT` 与 `-p 8000` 默认一致（`.env` 生成值即 8000），无感。
  - 服务重启：改 `.env PORT` 后重启 → 真实端口不变，`/api/version` 变化。
  - 运行期：无 shell-out，暂无功能影响。
- 验证命令（只读）：`grep -n "PATH=\|-p 8000\|EnvironmentFile" <快照>/deploy/gipfel.service` + `grep -rn "backendPort" <快照>/frontend/src`（证明确无消费方）；部署机只读复核 `systemctl show gipfel -p Environment`。

- 建议方向：`PATH` 改为追加系统目录（或直接不覆盖 PATH，只给 `ExecStart` 绝对路径）；明确"生产端口的唯一真源是 unit/nginx，`.env PORT` 仅供 rundaphne 与展示"，并修掉 `rundaphne.py` 的表述；`HOME` 若需使用则显式指定可访问目录（如 `StateDirectory=` 派生）。
