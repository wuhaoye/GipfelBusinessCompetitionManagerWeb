- **B3**：`stock/views.py` 新增 `_round2`（localcontext prec=60 quantize 0.01），`stock/engine.py` `round2` 改为 localcontext prec=70；旧的 `round(x*100)/100` 在服务端全部消失。

### 🔴 新增 E1：SQLite 上 Decimal 超 15 位有效数字静默丢精度（仓库自带测试 FAIL）

**实测**：`tests/sqlite_decimal_roundtrip.py`（写入 `12345678901234567890123.4567`）→ 输出 FAIL：

```text
写入值： 12345678901234567890123.4567
读回值： 12345678901234600000000.0000     ← 整数部分低 9 位丢失（1.23e22 被 REAL 化）
SQLite 存储形态： Decimal('12345678901234600000000.0000')
往返精确： FAIL
```

**根因**（SQLite 亲和性实测）：Django 为 DecimalField 声明的列类型是 `decimal` → SQLite **NUMERIC 亲和性**，插入的十进制文本会被强制转成 REAL 存储（SQLite 3.50.4 实测：`NUMERIC/DECIMAL/REAL/INTEGER` 亲和列均把 `'12345678901234567890123.4567'` 存为 `real`，仅 `TEXT` 亲和列保留原文）。读回时 Django SQLite 转换器再以 `Context(prec=15).create_decimal_from_float` 还原 → 仅保留 15 位有效数字。

**影响**：本次更新的 `max_digits=60` 账目字段（fuels/warehouses/stock/vehicles/infrastructures/production_lines…）在**默认 SQLite 库上无法精确存取 15 位以上有效数字**（10^13 级金额即开始出现分位误差，10^23 级完全不可用）；PostgreSQL 的 numeric 类型不受影响。这与「SQLite 默认、千万京目标」的设计冲突。

**建议修复**：为 DecimalField 提供 TEXT 亲和性存储（自定义 `db_type` 返回 `text` 的子类字段 + 重建列迁移；读回转换器对 TEXT 可精确还原），或至少在文档/运维中声明「大金额仅 PostgreSQL」并在 SQLite 上做写入侧防超 15 位有效数字的拦截（宁可报错不可静默丢值）。

### 🟡 新增 E2：引擎算术受全局 decimal 精度 50 位限制

`contracts/engine.py:39` 与 `company_fields/timer.py:34` 在**模块导入时修改全局** `decimal.getcontext().prec = 50`（实测：导入前 28 → 导入后 50）。实测 55 位有效数字的 Decimal 相加被静默舍入（`ADD == 期望` → False）。对目标量级（10^23 + 4 位小数 ≈ 28 位有效数字）完全够用，但：
- 超过 50 位有效数字（10^46 级以上）的算术会静默舍入（默认 ROUND_HALF_EVEN）；
- 各模块精度策略不统一：引擎全局 50、`stock/views._round2` localcontext 60、`stock/engine.round2` localcontext 70；
- 全局改 context 属隐式副作用，建议统一为局部 `localcontext`。

### 🟡 新增 E3：EXP/LOG 运算符经 float 中转（engine.py:1145-1147）

`apply_op` 的 `EXP/LOG` 使用 `math.exp(float(...))`：对超大参数（如 `EXP(1e23)`）会抛 OverflowError（math range error）→ 未捕获则接口 500；且结果精度为 double（对一般量级无碍）。数学函数输出若回写 NUMBER 字段，会经 `to_number(float)` 的 `repr()` 无损回转，但函数值本身只有双精度。公式表达式内置函数（sin/cos 等）同理。

## 4. 补充观察

- 旧数据库中的历史 float artifact 字符串（如 `"0.30000000000000004"`）仍可被读取为精确 Decimal 参与比较——不再产生新误差，但存量数据如需回写清理需专项数据修复。
- `renderers.py` 对**小数 Decimal 一律转字符串**出站（如 `"12.3450"`），前端契约从 number 变为 string/number 混合，接口消费者（含历史调用方/外部脚本）需按 `formatMoney`/`isValidNumberString` 语义处理；仓库内前端已适配，文档（API接口文档.md）需同步说明。
- 本次复测为运行仓库自测与探针重建了 `backend/.venv` 与 `backend/db.sqlite3`（gitignore 内开发产物），未改动任何业务代码。

## 5. 结论

- v2 报告的**关键缺陷（A1-A3、D2-D4 与出站大数 B1/D5）已实质修复**，账目管线整体已切换为 int/Decimal 精确算术 + 大数安全出站/展示。
- **必须处理**：E1——SQLite 默认库无法精确存储 15 位以上有效数字的 Decimal（仓库自带回环测试已 FAIL），与千万京目标冲突；建议 TEXT 亲和列或 PostgreSQL-only 策略 + 防超限拦截。
- 建议跟进：E2（localcontext 化与统一精度）、E3（EXP/LOG 大参数溢出防护）、B2 前端图预览/行情页 Number 化、B4 写入校验与存量 artifact 清理、C1 剩余 FloatField（含 research_cost）清理。
