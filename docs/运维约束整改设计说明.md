## 0. 总原则：零配置即等价于改造前

### 0.1 ⚠️ 对简报 C1 机制的重要更正（实施期实测，结论已改变 C1-a 的定性）

简报 C1.1/C1.3 断言「全部同步视图共用一个线程（asgiref 进程级 `single_thread_executor`，max_workers=1），
8 并发 = 1.61s 串行」。**该断言在真实请求路径上不成立**：

- 简报的测法（直接 `await sync_to_async(work, thread_sensitive=True)(...)`，无外层上下文）确实串行；
- 但 Django 的 ASGI handler 在**每个请求**外面包了 `async with ThreadSensitiveContext():`
  （`backend/.venv/Lib/site-packages/django/core/handlers/asgi.py:169`），
  而 asgiref 在此上下文生效时走的是**该上下文专属的** `ThreadPoolExecutor(max_workers=1)`
  （`asgiref/sync.py:467-478`），只有**无**上下文时才落到进程级 `single_thread_executor`（`asgiref/sync.py:488`）。
- 实测（`tests/c1_mechanism_probe.py`，Lead 独立复现；verifier 另有 daphne 真机形态对照）：

  | 形态 | 8 并发墙钟 | 不同线程数 |
  | --- | --- | --- |
  | A 无上下文（= 简报 C1.3 的测法） | **1.61s（串行）** | 1 |
  | B 每任务一个 `ThreadSensitiveContext`（= 真实请求路径） | **0.20s（并行）** | 8 |
  | C 同一上下文内 8 个任务（= 单个请求内多段同步工作） | **1.61s（串行）** | 1 |

  真实 daphne（`backend.asgi:application` + 慢中间件）实测：N=20 并发墙钟 **0.27s**、最大同时 sleep=21。

**因此**：
1. C1-a **不是**「消除单线程串行」的必需项 —— 简报 C1.5 的两条并发验收在**改造前形态下就已达标**；
2. C1-a 仍然值得做，但其收益要改为：**有界线程池/背压**（daphne 为每个在途请求新建一条线程，
   无上限；gunicorn `4×8=32` 线程 + 队列给出确定上限与排队语义）、
   **长连接与短请求进程隔离**（Socket.IO 不再与 REST 争同一 event loop / 同一次重启）、
   以及可独立重启/限流/观测的进程边界；
3. 真正的产能瓶颈在别处：**SQLite 单写者 + 5s 锁等待（C2）**、审计写放大（C2）、
   请求量放大（C3）。这两块才是本批次里性价比最高的整改。
4. C1-a 的新增风险面（跨进程总线、`/_internal/` 端点与门禁白名单、双 unit、限流）已逐条登记，
   并保留一键回退（§5）。

### 0.2 总原则：每一项都可开关、可回退；但"零配置"不等于"逐字节等于改造前"

**准确表述**（独立验收实测后的更正）：

| 项 | 零配置（`.env` 不写任何新键）下的行为 | 是否是"改造前的行为" |
| --- | --- | --- |
| C1-a 总线 | `REALTIME_BUS=auto` → 无 Redis/无转发配置时解析为 `local`（进程内 deque + loop 投递） | ✅ 是（与改造前一致） |
| C2 SQLite | `SQLITE_TUNING_ENABLED=true` → 新连接 `WAL / busy_timeout=20000 / synchronous=NORMAL` | ❌ **否，默认已整改**（这正是整改目标） |
| C2 审计 | `AUDIT_HTTP_ERROR_MODE=sampled` → 4xx 采样 5% 落库 + 100% 写日志 | ❌ **否，默认已整改** |
| C3 心跳 | `AUTH_ME_CONDITIONAL_ENABLED=true` → `/auth/me` 返回 `ETag`（条件请求与 `light` 由前端使用） | ❌ **否，默认已整改**（响应头新增，响应体不变） |
| C1-a 进程拓扑 | 只有部署形态决定（是否启用 `gipfel-wsgi.service` + nginx 上游拆分） | ✅ 是（不启用即单进程 daphne） |

**逐项回退开关（要"完全回到改造前"需四项一起，缺一不可）**：

| 目标 | 开关 / 操作 |
| --- | --- |
| C1-a 进程分离 | 停 `gipfel-wsgi`；nginx `upstream gipfel_django` 指回 `127.0.0.1:8000`；`.env` 设 `REALTIME_BUS=local` |
| C2 SQLite 调优 | `.env` 设 `SQLITE_TUNING_ENABLED=false`（→ 不再下发 PRAGMA 且撤掉 `OPTIONS["timeout"]`）；若要连**库文件**也从 WAL 变回 `delete`，需停服后显式 `PRAGMA journal_mode=DELETE`（`journal_mode` 是文件持久属性） |
| C2 审计降噪 | `.env` 设 `AUDIT_HTTP_ERROR_MODE=all` |
| C3 心跳条件请求 | `.env` 设 `AUTH_ME_CONDITIONAL_ENABLED=false`（不再返回 ETag / 不校验 If-None-Match / 忽略 `light`） |
| C3 前端行为 | 前端是**构建产物**：重新发布旧 `frontend-dist` 即回退（后端接口全部向后兼容） |

所有整改项都设计成**可开关、可回退**：除上表所列"默认已整改"的三项（C2 SQLite、C2 审计、C3 ETag）外，
其余行为在零配置下与改造前一致；C1-a 的进程分离只在部署启用第二个 unit + nginx 拆分时才生效。

红线（简报 §C1.6 / §C2.4「不该做」）：不直接多开 daphne 抢端口、不给同步视图加 `async_to_sync` 包装、
不依赖 `thread_sensitive=False` 混用、不热拷活库、不因为「开了 WAL」就认为写可以并行。

## 2. 跨进程事件总线（C1-a 代码侧）

新增 `backend/apps/realtime/bus.py`，作为 emit 的**唯一投递出口**；`emit.py` 的公开 API
（`emit_resource_changed` / `emit_resource_changed_to_users` / `emit_to_users` / `emit_to_competition` /
`emit_system_event` / `emit_system_restored` / `emit_permissions_changed` / `kick_user_sessions` /
`replay_since` / `server_seq` / `register_loop`）**签名与语义保持不变**——
调用方（`apps/common/signals.py`、`apps/snapshots/*`、各视图）不得改动。

模式（`settings.REALTIME_BUS`）：

| 模式 | 谁用 | 行为 |
| --- | --- | --- |
| `local` | 单进程（默认落点） | 进程内 deque 环形缓冲 + 进程内 seq + `run_coroutine_threadsafe` 投递（= 改造前） |
| `hub` | daphne unit | 同 local，并**额外开放内部转发端点**；收到转发事件时分配 seq/入环/投递房间 |
| `forward` | WSGI unit | emit 打包后 POST 给 `REALTIME_FORWARD_URL + /_internal/realtime/emit`，由 hub 分配 seq 并投递；转发排队在**独立后台线程**，业务请求不等待 |
| `redis` | 两端 | `client_manager=AsyncRedisManager`；seq 用 Redis `INCR`，环形缓冲用 Redis `ZSET`（score=seq，超长按 rank 裁剪） |

内部端点契约：
- `POST /_internal/realtime/emit`（`settings.REALTIME_INTERNAL_PATH`），JSON
  `{"event": str, "payload": obj, "room": str|null, "replay": bool=?, "action": "emit"|"kick"=?}`；
- 请求头 `X-Gipfel-Internal-Token: <settings.REALTIME_INTERNAL_TOKEN>`（由 `LOGVIEWER_SECRET_KEY` 派生，`secrets.compare_digest` 比较）；
- 仅接受回环来源（`REMOTE_ADDR` ∈ {127.0.0.1, ::1}），非回环/无令牌/令牌错 → 403；
- 成功返回 `{"ok": true, "seq": <int>}`；**不做再转发**（防自环）；
- 必须 `csrf_exempt`，并把 `/_internal/` 加入 `apps/snapshots/middleware.py::EXEMPT_PREFIXES`
  （否则暂停/回退期间 `system:paused` 自身的转发会被 423 拦掉 = 广播断链）。

> **两个增量可选字段（实现期批准，缺省即契约原文行为）**：
> - `replay`（缺省 `true`）：控制 hub 侧是否把该事件写入重放环形缓冲。`emit_to_users` /
>   `emit_resource_changed_to_users` / `emit_to_competition` / 控件包通知在 local 模式下**不入环**，
>   转发时必须带上 `replay=false`，否则重连 `sync:replay` 会重复补发（语义漂移）。
> - `action`（缺省 `"emit"`，可选 `"kick"`）：`kick_user_sessions()` 在 local 模式下会**真正断开** socket
>   （`sio.disconnect`，审计 I-01/I-03 的修复）。forward/redis 模式下 WSGI 进程拿不到 daphne 侧的 sid，
>   故把 kick 交给 hub 执行；只要 `REALTIME_FORWARD_URL` 非空就走这条通道，纯 redis 且无 hub 直连时
>   退化为 `auth:required` + warning（已知残余限制，写入报告）。

降级要求（**不允许**因缺少依赖而崩）：
- `redis` 包未安装或连接失败 → 记 warning，回落到 forward/local，实时功能不停摆；
- `forward` 模式但 hub 不可达/超时 → 丢弃该事件 + warning（与改造前「loop 未就绪静默降级」一致），**不抛给业务**。

## 3. C2 阶段 1（SQLite 调优 + 审计降噪）

settings 侧（已完成，见 `backend/backend/settings.py`）：
`SQLITE_TUNING_ENABLED` / `SQLITE_JOURNAL_MODE=WAL` / `SQLITE_SYNCHRONOUS=NORMAL` /
`SQLITE_BUSY_TIMEOUT_MS=20000` / `SQLITE_WAL_AUTOCHECKPOINT` / `SQLITE_PRAGMA_STATEMENTS` /
`AUDIT_HTTP_ERROR_MODE=sampled` / `AUDIT_HTTP_ERROR_SAMPLE_RATE=0.05` / `AUDIT_RETENTION_DAYS=7`。

接线要求：
- `apps/common/db_pragmas.py`（新增）：`connection_created` 信号处理函数，逐条执行 `SQLITE_PRAGMA_STATEMENTS`，
  失败只记 warning 不阻断连接；`apps/common/apps.py::ready()` 里 `connect()`。
  注意 Django 5.0 的 sqlite3 后端**不支持** `OPTIONS["init_command"]`（OPTIONS 会原样传给 `sqlite3.connect`），
  只用 `OPTIONS["timeout"]`（→ `PRAGMA busy_timeout`）+ 信号两层。
- 审计降噪只作用于 `log_exception`（HTTP 异常上下文）；`log_write`（业务写审计）**永远落库**；
  5xx 在 `sampled` 模式下也**全量落库**；4xx 采样落库 + 始终 `logger` 记录（含 method/path/status/operator）。
- 新增 `manage.py audit_archive`：默认 `--days AUDIT_RETENTION_DAYS`，先导出 `logs/audit_archive/audit-<日期>.jsonl.gz`
  再分批删除；导出失败则**不删除**；支持 `--dry-run`、`--no-archive`、`--batch-size`。

## 4. C3 接口契约（后端 ↔ 前端）

### 4.1 `GET /api/auth/me`（只增不改）
- 无参：响应体与改造前**逐字段一致**；新增响应头 `ETag`（弱校验亦可，须稳定）。
- `If-None-Match` 命中当前 ETag → **304**，空体，带同一 `ETag`。
- `?light=1` → `data` 仅 `{id, tokenVersion, isActive, mustChangePassword}`（全局信封 `{code,message,data}` 不变）。
- 401（失效/被顶号/强制改密门禁）语义**完全不变**——心跳靠它感知顶号。
- 开关 `AUTH_ME_CONDITIONAL_ENABLED=false` 时回到改造前行为。

### 4.2 `GET /api/company-fields?companyIds=1,2,3`（新增，批量）
- 逐个 `/company-fields/{cid}`（GET/PUT）与 `/company-fields/{cid}/{fieldId}` **原样保留**。
- 无 `updatedAfter` → 全量：`data = {companyIds:[…], serverTime:"<ISO>", companies:{"1":{"industryTypeId":…,"fields":[…]}, …}, missing:[…]}`。
- 带 `updatedAfter` → 增量：`data` 追加 `incremental:true`；每个公司对象内为 `{industryTypeId, fields(仅变更/新增), existingIds, incremental:true}`，
  请求带 `previousIds` 时另附 `deletedIds`（语义与 `apps/common/sync.py` 既有口径一致）；顶部 `serverTime` 为查询前时间，可作下一基线。
  > ⚠️ **实施期更正**：原设计说「与单公司协议同构」，但核对代码后确认**单公司 `GET /company-fields/{cid}` 从来没有增量协议**
  > （原文只返回 `{industryTypeId, fields}`，前端那条 `updatedAfter` 增量分支是长期不生效的死代码）。
  > 为守住「既有端点原样保留、行为不变」的红线，**增量只做在批量端点**，单公司端点保持原样；
  > 因此重连对账必须走批量端点（单公司分组回落单点 = 与改造前同样的无增量行为，非回归）。
- 权限：逐公司套用与单公司端点**完全相同**的作用域校验；无权/不存在的公司进 `missing`，**不得**返回其数据。
- 上限 50（去重后）：>50 → 400；`companyIds` 缺失/全空/含非数字 → 400；`updatedAfter` 无法解析按全量处理（沿用既有口径）。

### 4.3 前端（C3）
- 心跳：可见 20s / 页面隐藏 60s；`light=1` + `If-None-Match`；304 视为成功；`mustChangePassword` 期间不启动；
  401 仍由全局拦截器接管（清登录态 + `auth:kicked`）。
- 重连对账：并发上限（默认 2）+ 指数退避 + 抖动；批量端点替代逐个公司产业字段请求；批量失败回落单点端点。
- 兼容：`reconcileAllIncremental` 之外的行为（`sync:reconciled` 事件、基线推进、IndexedDB 缓存）不得改变。

### 4.4 nginx 限流（C3，避免误伤）
- `/api/`：`limit_req`（按 `$binary_remote_addr`，取值需容忍「全场同一个 NAT 出口 IP」）+ `limit_conn`；
- `= /api/auth/login`：单独更严的 zone；`= /api/health` **不限流**（监控用）；`/socket.io/` 只限连接数不限速；
- 超限返回 **429**；access log 增加 `$request_time`（自定义 `log_format`，名字唯一，写在 file 顶层= http 上下文）。
- 每个数值必须有注释说明「为什么是这个值」（正常单人 ≤5 req/s、100 人同一出口 IP 的估算）。
